# 方案一 · 部署指南 —— 镜像构建、扁平布局装配、网关启动与变更流

> 设计原理见 [`方案一-01-设计与架构.md`](方案一-01-设计与架构.md)，实测方法与结论见 [`方案一-03-测试方案.md`](方案一-03-测试方案.md)，
> 实测/踩坑见 [`方案一-04-实测踩坑实录.md`](方案一-04-实测踩坑实录.md)。本文覆盖：前置条件 → 密钥/环境纪律 →
> jumphost 构建镜像 → 实例扁平布局装配 → 网关启动 → 部署后自检 → 变更流 → 停服/拆除。
>
> ⚠️ 方案一**没有** `deploy.sh` 那样的单命令编排器——它不建 EC2/网络/CA，只是在一台**已存在的**实例上
> 装配容器。实例的创建、IAM 角色、SSM Online 是前置条件，不在本文脚本范围内。

---

## 1. 前置条件

| 项 | 要求 |
|---|---|
| AWS 凭证 | `default` profile（全球区，us-west-2）；`sts get-caller-identity` 能过 |
| 本地工具 | `aws`（CLI v2）、`base64`、`python3`（`ssm_exec.sh` 用它拼 JSON 参数） |
| 目标实例 | `kiro-dlp`（`<TEST_INSTANCE_ID>`，m7i.2xlarge，8c/32G，x86_64，us-west-2，私网 172.31.27.174）；**SSM Online**，本机有 `ssm:SendCommand` 权限 |
| 登录方式 | 仅 SSM Session Manager（**无 SSH key**，不开 22/公网）；`aws ssm start-session` 或经 `ssm_exec.sh` 投递脚本 |
| 镜像构建机 | `jumphost`（x86_64，与 kiro-dlp 同架构）——**所有 `docker build/save` 在此跑**，kiro-dlp 只 `docker load`，不 login/push/pull（aws-env 合规约定） |
| 实例 IAM 角色 | 带 `bedrock:InvokeModel`（`qwen.qwen3-32b-v1:0` / `meta.llama3-1-8b-instruct-v1:0`）；**IMDS hop-limit=2**（容器内经 IMDS 取临时凭证，**不落长期 AK/SK**） |
| 中转桶 | 一个自有 S3 桶（`sync_engine.sh` 走 presigned URL 中转大 payload；实例侧只需 `curl`，无需 S3 权限） |

> ⚠️ **并发凭证冲突**：破坏性/批量 AWS 操作时，多个 Claude 会话共用同一 `default` 凭证会互相踩踏。
> 部署期间避免并发会话，排查用 CloudTrail `invokedBy` + 会话检索定位。

## 2. 环境变量与密钥纪律

### 2.1 本机脚本变量（`ssm_exec.sh` / `sync_engine.sh` 需要）

```bash
export KIRO_DLP_INSTANCE="<TEST_INSTANCE_ID>"   # 目标实例 ID（不硬编码进脚本）
export KIRO_DLP_S3_BUCKET="<自有中转桶>"          # sync_engine.sh 走它中转 engine/
```

### 2.2 网关容器 env（compose 启动时读，见 `docker/docker-compose.gateway.yml`）

```bash
# —— admin key：启动前必须自备，刻意不留默认值 ——
export LITELLM_MASTER_KEY="sk-$(openssl rand -hex 24)"
#   ★ compose 里用 ${LITELLM_MASTER_KEY:?...} 而非 :- ——默认值会静默成为网关 admin key
#     （可签发虚拟 key、读全部日志/开销）。宁可启动失败，也不留固定默认值。

# —— L4 Bedrock 标定开关（默认 0 = 关；仅阶段4 短暂置 1）——
export DLP_L4_BEDROCK=0
#   ★ 红线：Bedrock = 数据出 VPC，仅功能验证非生产；置 1 标定完必须还原 0（见 §7.2）。
```

其余 env 在 compose 里已固化：`AWS_REGION=us-west-2`、`PRESIDIO_ANALYZER_URL=http://presidio-analyzer:5002/analyze`、
`DLP_METRICS_PATH=/metrics/dlp_gateway_metrics.jsonl`（挂 `dlp-metrics` 卷，压测/对账读它）。

## 3. 在 jumphost 构建镜像（save | load 合规链路）

两个镜像都在 `jumphost`（x86_64）构建，`docker save | ssh kiro-dlp docker load` 传过去；kiro-dlp 不 pull。

```bash
# 引擎镜像（含 dlp 源码 + tests + fixtures；纯 stdlib，可选依赖装失败不阻塞）
ssh jumphost 'cd <仓库路径> && docker build -f docker/Dockerfile.engine -t kiro-dlp-engine:latest .'
```

```bash
# Presidio 中文增强镜像（官方镜像 + zh_core_web_sm + en/zh 双语 NLP 配置）
ssh jumphost 'cd <仓库路径>/docker && docker build -f Dockerfile.presidio-zh -t presidio-analyzer-zh:latest .'
```

```bash
# 传到实例（save | load；kiro-dlp 无 SSH key，经中转机或 SSM 端口转发，视实际链路）
ssh jumphost 'docker save kiro-dlp-engine:latest presidio-analyzer-zh:latest' \
  | ssh kiro-dlp 'docker load'
```

> LiteLLM 用官方 `ghcr.io/berriai/litellm:main-latest`（compose 里声明），若 kiro-dlp 不能直接拉，
> 同样在 jumphost `docker pull` 后 `save | load`。

## 4. 实例扁平布局装配

实例上的目录布局**扁平**，与仓库三层结构**解耦**：

```
/home/ec2-user/kiro-dlp/
├── engine/     ← dlp 源码包 + tests + fixtures（由 sync_engine.sh 拼装）
├── gateway/    ← litellm_config.yaml / dlp_guardrail.py / test_gateway.py / bench_gateway.py
└── docker/     ← docker-compose.yml + docker-compose.gateway.yml
```

> ★ 正因为布局扁平，`docker-compose.gateway.yml` 里的 `../gateway`、`../engine` 是**实例布局**相对路径
> （从 `docker/` 看命中同级目录），**不是仓库布局**。仓库里 gateway 归在 `方案一-litellm-gateway/gateway/`、
> engine 在根 `engine/`——浏览仓库时勿按目录树直接解析那两行（详见 compose 文件头注释）。

### 4.1 同步引擎源码（`sync_engine.sh`，S3 presigned 中转）

```bash
cd 方案一-litellm-gateway/testing/remote
./sync_engine.sh
```

它把仓库根 `engine/` 下 `dlp/*.py` + `tests/*.py` + `tests/fixtures/*.json` + `tests/fixtures_layers/*.json`
打包 → 传中转桶 → 生成 15 分钟 presigned URL → SSM 让实例 `curl` 下载解包到 `engine/`，末尾打印同步了
几个文件。**改了本地 `engine/dlp/*.py` 或 fixtures 后重跑它即可。**

### 4.2 同步网关文件 + compose

`gateway/`（`litellm_config.yaml`、`dlp_guardrail.py`、测试脚本）与 `docker/`（两个 compose）也需在实例
对应目录就位。可比照 `sync_engine.sh` 的 S3 中转方式推送，或经 SSM `base64` 投递小文件。**关键：
`docker-compose.gateway.yml` 必须与 base `docker-compose.yml` 同处实例 `docker/` 目录**——它是 base 的
override，Docker 规则要求 override 的相对路径按 base 目录解析（见 01 §7 与 compose 文件头）。

## 5. 启动网关（base + 网关叠加层）

两个 compose 同处 `docker/`，用 `-f` 叠加启动 presidio + litellm：

```bash
export LITELLM_MASTER_KEY="sk-$(openssl rand -hex 24)"   # 先备好 admin key
cd /home/ec2-user/kiro-dlp/docker
docker compose -f docker-compose.yml -f docker-compose.gateway.yml up -d presidio-analyzer litellm
```

- `presidio-analyzer`（:5002 内网，`presidio-analyzer-zh:latest`）先起，litellm `depends_on` 它
  `service_healthy` 才启动。
- `litellm`（:4000）挂 `CorpDLPGuardrail`——volume 挂 `../gateway/litellm_config.yaml`、
  `../gateway/dlp_guardrail.py`、`../engine/dlp`（引擎源码包）。
- 端口 `4000:4000` **仅实例内 / SSH 隧道 / SSM 访问，安全组不对公网开 4000**。

> **压测对照容器**（阶段3 才需要）：另起一个 `litellm-nodlp`（:4001，配置用 `litellm_config_nodlp.yaml`，
> 无 guardrail），用于分离「上游 Bedrock 延迟」与「DLP hook 成本」。它不是常驻组件。

## 6. 部署后自检

进 kiro-dlp 的 SSM 会话（或经 `ssm_exec.sh` 投递）：

```bash
# 1. 容器状态
sudo docker ps --format '{{.Names}}\t{{.Status}}' | grep -E 'litellm|presidio'

# 2. presidio 健康（内网 :5002）
sudo docker exec presidio-analyzer python -c \
  "import urllib.request; print(urllib.request.urlopen('http://localhost:5002/health',timeout=3).status)"

# 3. 网关 /v1/models（需 admin key）
KEY=$(sudo docker inspect litellm --format '{{range .Config.Env}}{{println .}}{{end}}' \
      | grep '^LITELLM_MASTER_KEY=' | cut -d= -f2-)
curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $KEY" http://localhost:4000/v1/models
```

期望：两容器 `Up`、presidio `200`、`/v1/models` `200`。随后即可跑
[`方案一-03-测试方案.md`](方案一-03-测试方案.md) §6 的分阶段测试（离线 56、网关 46、压测、L4 标定、分层完备），
复现命令见 [`testing/README.md`](testing/README.md)：

```bash
cd 方案一-litellm-gateway/testing/remote
./ssm_exec.sh host_stage1_offline.sh          # 离线 56 条，约 30s
./ssm_exec.sh host_stage2_gateway.sh 900      # 网关集成 46 条，约 1 分钟
```

## 7. 变更流

### 7.1 改了引擎 / guardrail 源码

```bash
# 1. 同步引擎源码到实例
cd 方案一-litellm-gateway/testing/remote && ./sync_engine.sh
# 2. guardrail 挂载的是 /app/dlp 源码 → 重启 litellm 让它重新加载
#    （在 kiro-dlp 上，或经 ssm_exec.sh 投递）
sudo docker restart litellm
```

> `host_stage2_gateway.sh` 的注释里也标了这条：**改过 `engine/dlp` 源码，阶段2 前必须
> `sudo docker restart litellm`**，否则测的是旧代码。

### 7.2 开/关 L4 Bedrock 标定（红线操作）

```bash
# 开（仅阶段4 功能标定；数据出 VPC，非生产）
cd /home/ec2-user/kiro-dlp/docker
export $(sudo docker inspect litellm --format '{{range .Config.Env}}{{println .}}{{end}}' | grep '^LITELLM_MASTER_KEY=')
export DLP_L4_BEDROCK=1
sudo -E docker compose -f docker-compose.yml -f docker-compose.gateway.yml up -d litellm

# 关（标定完必做；host_stage4_l4.sh 已内置这步 + 末尾校验 /proc/1/environ 里 DLP_L4=0）
export DLP_L4_BEDROCK=0
sudo -E docker compose -f docker-compose.yml -f docker-compose.gateway.yml up -d litellm
```

**红线**：L4 Bedrock 后端仅功能验证，跑完必须还原 `DLP_L4_BEDROCK=0`（见 01 §6 红线 1/2）。

## 8. 停服与拆除

方案一不创建 EC2/网络/CA，故**没有 `cleanup.sh`**；停服 = 停容器，不影响实例本体。

```bash
# 停网关（保留镜像与实例）
cd /home/ec2-user/kiro-dlp/docker
docker compose -f docker-compose.yml -f docker-compose.gateway.yml down

# 如需连 presidio 一起停，down 不带服务名即可（上面 down 已停 compose 内全部服务）
```

**刻意不碰**：实例本体、IAM 角色、镜像（`kiro-dlp-engine` / `presidio-analyzer-zh`）；这些是可复用
基础设施。若要彻底回收实例，属实例生命周期管理，不在本方案脚本范围。

> **回滚到「无 DLP」**：本质上把客户端 `base_url` 指回真实上游即可（opt-in 的天然属性——不接入网关
> 就完全不过 DLP）。无需像方案二那样操作 CA/nginx map。
