## 1. 阶段1 首轮：Presidio 弱 NER 把良性中英文判成 PII（套件2 8/16、套件6 2/4）

**症状**：离线 56 条首轮跑，误报基线**套件 2 只过 8/16**（8 条 `expected=pass` 被判 REDACT），
语义缺口**套件 6 只过 2/4**（本该同步 pass 的业务逻辑被误 redact）。两条硬门（套件1 漏拦 0、
套件2 误报 0）里的误报门直接破了。

**数据证据**（探针取 Presidio 原始输出坐实，非猜）：

- **S2-03**：整段中文被 en 模型标成一个 `PERSON`，置信度 **0.85**；
- **S2-06**：hex/base64 片段 `86d081884c…` 被 zh 模型标成 `PERSON`；
- **S2-16**：开源项目名 `nightingale`（小写社区版）被标成 `LOCATION`；
- **S2-14**：运单号恰好过了 Luhn 校验，Presidio `CREDIT_CARD` 给满分 **1.0**。

**根因**（三个，全在 Presidio NER 的统计特性，不在方案一网关逻辑）：

1. **弱实体恒高分**：Presidio 对 spaCy NER 实体（PERSON/LOCATION）**恒给 0.85**，
   单纯调阈值区分不了真假——真人名和「把中文句子整段吞成人名」都是 0.85。
2. **跨语言 NER 乱标**：en 模型看中文、zh 模型看 hex 串，都会高置信度胡说。
3. **流水号降权不足**：原实现对「运单号/流水号」语境做 `-0.4` 降权，但 Luhn 满分 1.0
   减 0.4 后仍 0.6，越过阈值。

**修法**（改共享引擎 [`engine/dlp/l3_presidio.py`](../engine/dlp/l3_presidio.py)，**不是改 fixture 迁就**）：

- **`_ner_plausible` 合法性过滤**：`PERSON/LOCATION` 列为**弱实体**——含数字/句读/跨语言 CJK
  混杂的片段、超长片段直接丢弃（一段中文句子不可能是一个人名）。
- **强实体佐证规则**：弱实体**只有在同一次扫描里存在模式类强实体**（EMAIL/PHONE/CN_ID/
  CREDIT_CARD 等有确定性正则的类）时，才参与**同步**裁决；否则交 L4 异步。这样孤立的弱 NER
  命中不再单独触发同步 redact。L3-09「多实体组合 redact」语义保留（mock 回放验证 PERSON+EMAIL
  仍双命中）。
- **流水号钳分**：流水/批次号语境下 `CREDIT_CARD` 置信度**直接钳到阈值下**（`min(score, 0.4)`），
  不再靠减法。

修复后离线**56/56，套件2 误报归 0、套件6 同步全 pass**（业务逻辑只能靠 L4 异步，与设计一致）。

> 教训：**统计检测器（NER/熵）的误报是机制性的，不能逐例调阈值糊。** 弱实体必须要么有确定性
> 强实体佐证、要么降级到异步告警——这是「best-effort 检测别把网关搞成误报机」的底线。

## 2. 「新引擎 45/56、旧引擎 56/56」—— 一次教科书级的测量假象

> 这是**共享引擎**在分层迭代打补丁时踩过的坑。方案一的阶段1 离线跑的是**同一套**
> [`run_offline.py`](../engine/tests/run_offline.py)，同一套 Presidio 依赖——这个陷阱对方案一
> 的离线 harness **原样适用**，故必须写进方案一的踩坑录。

**症状**：给引擎打完一批补丁后，观察到**新引擎离线只过 45/56**（11 条 `expected=pass` 被判
REDACT），而**旧引擎（无补丁）过 56/56**。第一反应：补丁引入了回归。

**两条独立证据推翻「回归」判断**：

1. **直扫探针绕过引擎**：用 `l3_presidio.scan` **完全绕过 `engine.py` 聚合**，直接对这 11 段
   良性文本跑——照样命中 PERSON/LOCATION/CREDIT_CARD。⇒ 命中源自 **Presidio NER 本身**，
   与引擎版本无关。
2. **同一在线 Presidio 下新旧引擎跑同一 fixture**：**逐行字节级完全一致**，都是 11 条 REDACT。

**真相**：那次「旧引擎 56/56」是旧引擎跑的时候 **Presidio 处于命中缺席态**（中文模型未加载 /
服务不可达）。这 11 例 `expected=pass`（`top_layer=None`），Presidio 缺席时它们**根本没产生 L3
命中** → verdict 自然 = pass = expected → 直接判 **PASS**，于是「全绿」。注意这**不是**被
`run_offline.py` §9 的「L3 skipped → SKIP」豁免掩盖的——那条豁免只对 `expected.top_layer=="L3"`
的用例生效（`_l3_absent(result) and verdict==pass`），这 11 例 `top_layer=None`，压根不落进该分支，
纯粹是 presidio 那次没命中而已。反过来，新引擎跑时 presidio **在线**，对这 11 段良性文本照其固有
NER 噪声命中（邮箱→LOCATION、代号 `falcon`→PERSON、"华东区"→PERSON+LOCATION）→ REDACT ≠ 期望
pass → 判 fail。这 11 例是 §1 修复后仍残留的 Presidio 固有噪声，**不是补丁 bug**。

> 教训（对方案一阶段1 直接适用）：**offline harness 判 PASS 前必须确认 Presidio 在线；
> 「某版本更绿」可能只是它跑的时候依赖服务缺席。任何跨版本 A/B，必须固定同一在线依赖再比。**
> 方案一的 [`host_stage1_offline.sh`](testing/remote/host_stage1_offline.sh) 因此在 `--network
> docker_default` 下跑，确保引擎容器能连到同一个在线 presidio。

## 3. 孤儿容器偷核：同批用例扫描从毫秒暴涨到 14–29 秒

**症状**：阶段1 离线跑，单条扫描耗时 **14–29 秒**——但 §8.1 独占运行时明明只有 **9.6–96ms**。

**数据证据**：`docker ps` 显示上一轮遗留了多个以 `kiro-dlp-engine:latest` 为 ancestor 的
**孤儿容器**仍在跑，与本轮的 presidio（单核热点）在 8 核机上抢核。

**根因**：反复迭代测试时，用 `docker run` 起的一次性引擎容器没被 `--rm` 干净回收，累积成孤儿；
它们和 presidio 争夺 CPU，把本该毫秒级的扫描拖成十几秒——**测出来的延迟全是被污染的**。

**修法**（进 [`host_stage1_offline.sh`](testing/remote/host_stage1_offline.sh) 起跑前）：

```bash
sudo docker ps -q --filter ancestor=kiro-dlp-engine:latest | xargs -r sudo docker rm -f
```

按 ancestor 精确清掉孤儿再跑，延迟立刻回到毫秒级。

> 教训：**性能数字必须在干净、无抢核的环境下测。** 一次性容器一律 `--rm`；测延迟前先确认
> 没有同镜像的僵尸进程在偷核——否则测的是调度竞争，不是引擎性能。

### 3.1 上面这条"修法"本身埋了个雷：跨方案误杀常驻服务（2026-08-05 亲踩）

**症状**：2026-08-05 按当前引擎重跑阶段5，**方案一自己三段全绿、exit 全 0、毫无异常**。但去方案二验证节点
打一发探针时，`curl 172.31.27.174:9000` 变成 `Failed to connect` —— 方案二的 DLP inspect 服务**没了**。

**根因**：`--filter ancestor=` 匹配的是**镜像**，不是"我起的容器"。方案二常驻的 `kiro-dlp-http`（`:9000`
inspect 服务）跑的**正是同一个** `kiro-dlp-engine:latest`，于是被上面那条 `xargs -r docker rm -f` 一并
force-remove。回看我自己那轮 stdout，第一行打出来的容器 ID `884ee06ea82f` 就是它——**证据当时就在眼前，
只是没人会去核对一个"清理孤儿"步骤的输出**。

**这个坑最坏的性质是它静默**：被杀的是**另一个方案**的服务，方案一的判定信号（74/78、exit=0）完全正常，
不去看方案二根本发现不了。共享镜像 + 共享主机 = 任何按镜像做的批量操作都会跨方案生效。

**修法**（已进 [`host_stage5_layers.sh`](testing/remote/host_stage5_layers.sh)）：按**名字白名单**排除常驻服务，
只清 `docker run --rm` 留下的随机名孤儿：

```bash
KEEP_RE='^(kiro-dlp-http|litellm|litellm-nodlp|presidio-analyzer)$'
sudo docker ps --filter ancestor=kiro-dlp-engine:latest --format '{{.ID}} {{.Names}}' \
  | awk -v keep="$KEEP_RE" '$2 !~ keep {print $1}' | xargs -r sudo docker rm -f
```

**复原步骤**（当时实际用的，记下来供下次）：

```bash
cd /home/ec2-user/kiro-dlp && sudo docker compose -f docker-compose.dlp-http.yml up -d
```

复原后**必须复核三件事**，缺一件就可能带着残缺配置继续测：`/health` 返回
`{"status":"ok","engine":"ready","pool":4}`；容器内 L4 env 集齐全（**2026-08-11 起为**：`DLP_L4_MODE`（默认
`async`）/ `DLP_USE_BEDROCK_L4` / `DLP_L4_MODEL_KEY` / `DLP_L4_BLOCK_MIN_CONFIDENCE` / `DLP_L4_TIMEOUT_MS` /
`DLP_L4_EXECUTOR_WORKERS` / `DLP_L4_QUEUE_MAX`；当时事发时是旧五 env——`DLP_RUN_ASYNC_L4`/`DLP_L4_SYNC_BLOCK`
两个旧 flag 现已弃用、由 `DLP_L4_MODE` 取代，容器内**不应再有**）；
经 `/inspect` 打一轮三态自检（PASS/REDACT/BLOCK 的 `top_layer` 都对）。

> 教训三条：① **按镜像批量删容器 = 跨方案武器**，共享主机上必须按名字白名单排除常驻服务；
> ② **"我这边全绿"不等于"我没破坏别人"**——有副作用的清理步骤，其输出要跟测试断言一样被核对；
> ③ 复原后**验证到状态而非验证到进程**（health + env + 三态），`docker ps` 有这一行不代表配置还对。

## 4. 阶段2 flowback：被 Bedrock Converse 的工具序列约束卡了两轮（非 DLP 问题）

**症状**：网关集成阶段，flowback（工具返回值回流）类用例经 LiteLLM :4000 连续返回 **HTTP 400**，
一度怀疑是回流 hook 本身有问题。

**数据证据**：LiteLLM 报的是 `UnsupportedParamsError` 与
`Conversation blocks and tool result blocks cannot be provided in the same turn`——错误来自**上游
Bedrock Converse 协议**，不是 DLP guardrail（guardrail 的 BLOCK 是 `blocked_by_corp_dlp`，形态完全不同）。

**根因**：Bedrock Converse 对 tool 消息序列有**三连硬约束**，`test_gateway.py` 构造 flowback
上下文时违反了：

1. `assistant` 消息里的 `tool_calls` **必须有对应的 `tools=` 定义**，否则 400；
2. `tool` result 消息**不能与 `user` content 放在同一轮**；
3. 缺任一条，LiteLLM 直接透传上游 400。

**修法**：按约束重构 `test_gateway.py` 的 flowback 消息序列（先补 `tools=` 定义、把 tool result
单独成轮）。改完 flowback 回流 hook 实测生效：**S5-03**（tool 返回含身份证）redact ✅、
**S5-07**（干净 tool 返回）pass ✅。

> 教训：**集成测试翻车，先分清是「被测系统坏了」还是「脚手架不合上游协议」。** 错误信息的
> **来源域**（DLP 的 `blocked_by_corp_dlp` vs 上游的 `Converse` 约束报错）是第一判据——本次
> 两轮返工都花在没先看清 400 来自哪一层。

## 5. 阶段2 附带验证：session_window 跨消息拼接（这次是对的）

不是坑，是一个容易被漏测、这次**确认生效**的语义，记录以免误以为方案一逐条独立扫。

`async_pre_call_hook` 给引擎传 `session_window`（同请求内此前消息），覆盖**跨消息拆分密钥拼接**
（EVA-03）。阶段2 实测 **S5-04 / S5-06** 命中 BLOCK，命中来源标 `source=session-window`——
说明拆成两条消息发来的密钥被滑窗拼接后拦下，不是逐条独立判定漏过。这是方案一相对「无状态逐条
扫描」的一个必要正确性点。

## 6. 阶段3：长文本高并发下 Presidio 单核打满 —— 架构没错，部署配置错了

**症状**：压测里 `clean_long`（~2000 token）随并发升高急剧劣化：

| case | c1 p50 | c8 p50 | c16 p50 | c16 p95 | c16 qps |
|---|---|---|---|---|---|
| clean_short(~50tok) | 152 ms | 266 | 422 | 545 | 31.9 |
| **clean_long(~2000tok)** | **1061 ms** | **7371** | **7633** | **13816** | **1.42** |

短文本一切正常（DLP 单请求净成本 c1 下 152−107 ≈ **45ms**，`dlp-off` 对照 :4001 基线 ≈103–130ms），
**唯独长文本高并发把 p50 拖到 7.6s、qps 掉到 1.4**。

**数据证据**（`docker stats` 负载中采样）：`clean_long` 期间 `presidio-analyzer` **单核
84–107% 打满**，`litellm` 仅 1–8%，`litellm-nodlp` ≈0.1%。**m7i.2xlarge 其余 7 核全闲置。**

**根因**：长文本 × 多归一化变体 × 双语言（en_core_web_lg + zh_core_web_sm）的 Presidio HTTP 分析
是唯一热点，而**单副本 presidio 是单核的**——8 核机上只用 1 核，其余闲置，天然扛不住长文本高并发。

**结论（诚实定性）**：这是**部署配置问题，不是架构缺陷**。改进方向按性价比：
① presidio-analyzer 多副本 / gunicorn 多 worker 横向吃满 8 核；② 变体×语言扫描做长度分桶与
增量去重；③ 长文本切块并行。本轮**未做扩容复测**，如实记为遗留（03 §8.3 / §8.6）。

> 教训：**「DLP 慢」要先归因到具体组件再下结论。** `docker stats` 把三容器 CPU 拆开一看，
> 瓶颈是单副本 presidio 单核，不是 guardrail、不是网关、不是引擎主链路（纯 stdlib，<1ms）——
> 归因清楚了，「架构缺陷」就降级成「加 worker」。

## 7. SSM 远程投递的三个反复踩的坑

`kiro-dlp` 无 SSH key、仅经 SSM 操作，投递脚本时踩过三个坑，已固化进
[`ssm_exec.sh`](testing/remote/ssm_exec.sh) 与各 `host_*.sh`：

1. **整脚本必须 base64 编码再投**：脚本里的引号/`$`/换行经 SSM `AWS-RunShellScript` 的
   JSON 参数会被二次转义打碎。`ssm_exec.sh` 把**整个脚本** base64 编码，远端
   `echo <b64> | base64 -d | bash` 执行。
2. **`grep` 无匹配返回非零会中断 `set -e`**：host 脚本里做「确认没有 xxx」的 grep，无匹配时
   退出码 1 会让整个脚本提前失败——凡这类 grep 一律 `|| true` 兜住。
3. **后台 `nohup ... &` 会挂起 SSM 调用**：SSM 等所有子进程结束才返回，后台进程让调用**永久
   pending**。压测里的 `docker stats` 采样必须**前台限时**（如 `timeout N docker stats`）而非
   后台常驻。

> （附带：本机默认 shell 是 zsh，`${!arr[@]}` 这类 bash 间接数组展开在 zsh 下不工作——投到远端
> `bash` 执行的脚本没事，但本地拼脚本时别用。）

## 8. 阶段4：L4 Bedrock 标定的红线纪律 —— 开完必须还原

**背景**：阶段4 用 Bedrock（Qwen3-32B 主 / Llama-3.1-8B 对照）验证 L4 语义**功能可行性**，
需临时 `export DLP_L4_BEDROCK=1` 重启 litellm。实测 **main 4/4、control 3/4**（Llama 漏
`proprietary_tech` S6-03），**同步 verdict 污染 = 0**（L4 开启时 4 条同步全 pass，硬约束
「L4 永不写 verdict」回归通过）。

**红线**：Bedrock 后端 = **数据离开本 VPC**，仅功能标定、**绝不能作为生产配置**留着。若标定完
忘记还原，`DLP_L4_BEDROCK=1` 就成了一条常驻的**第二泄漏通道**（把放行面内容异步发往云端 LLM）。

**规避**：[`host_stage4_l4.sh`](testing/remote/host_stage4_l4.sh) 内置还原步骤——标定跑完
`export DLP_L4_BEDROCK=0` + 重新 compose + 校验容器 env 里 `DLP_L4_BEDROCK=0` 才算收工。
本轮**测毕已还原 0**（03 §8.4 / 8.0 均记录）。生产 L4 须自建（g6 vLLM / 客户 VPC GPU），数据不出 VPC。

> 教训：**任何「临时开启、数据出境」的开关都要有配套的自动还原 + 收工校验**，靠人记得关迟早出事。

## 10. 工程教训（可迁移）

1. **机制对不等于测量可信。** 方案一的合成规格很快就全绿，真正耗时的是「这个绿/红是不是真的」——
   依赖缺席（§2）、孤儿抢核（§3）、脚手架违约（§4）都能伪造结果。**先信任测量，再信任结论。**
2. **统计检测器的误报是机制性的，要靠结构约束治，不靠逐例调阈值。**（§1）弱实体要么有确定性
   强实体佐证、要么降级异步。
3. **跨版本 A/B 必须固定同一在线依赖。**（§2）「某版本更绿」常常只是它跑时某个服务没在线。
4. **性能数字要在干净环境测，并归因到具体组件。**（§3/§6）孤儿抢核会伪造延迟；`docker stats`
   拆容器 CPU 能把「架构缺陷」降级成「加 worker」。
5. **集成翻车先看错误的来源域。**（§4）DLP 的 `blocked_by_corp_dlp` 和上游的 Converse 约束报错
   长得完全不同——分清是被测系统还是脚手架，能省两轮返工。
6. **临时的、数据出境的开关必须自带自动还原 + 收工校验。**（§8）
7. **"我这边全绿"不等于"我没破坏别人"。**（§3.1）共享主机 + 共享镜像下，按镜像批量删容器会跨方案生效，
   而受害方案的故障**不会出现在你的判定信号里**。有副作用的步骤，其输出要和测试断言一样被核对；
   作用域能写死就写死（按名字白名单 > 按镜像过滤）。
7. **诚实标注未做项。** 长文本高并发的 presidio 扩容复测本轮没做，如实记为遗留（§6），
   不拿短文本的 45ms 净成本粉饰长文本 7.6s 的劣化。
