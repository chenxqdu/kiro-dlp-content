# 方案一 · 设计与架构 —— opt-in LiteLLM TLS 终止网关 + VPC 内 DLP 联动

> 本文是方案一的纲领文档，说明**为什么这样设计、每个组件做什么、哪些是绝不能碰的红线**。
> 部署步骤见 [`方案一-02-部署指南.md`](方案一-02-部署指南.md)，实测方法与结论见 [`方案一-03-测试方案.md`](方案一-03-测试方案.md)，
> 真机/实测踩坑见 [`方案一-04-实测踩坑实录.md`](方案一-04-实测踩坑实录.md)。目录导航见 [`README.md`](README.md)。

## 0. 一句话定位

方案一 = **一台 opt-in 的 LiteLLM TLS 终止网关**：客户端（自研 Agent / SDK）主动把 `base_url` 指向
本网关，网关做 TLS 终止、成为**合法的明文终点**——**无需伪造证书、无需分发企业 CA**。拿到明文后，
网关内挂的 `CorpDLPGuardrail`（LiteLLM 的 `pre_call` + `pre_mcp_call` 两个 hook）把 prompt / 工具返回值
回流 / MCP 工具调用参数同步送**同 VPC 内的 DLP 引擎**裁决，按 `PASS / REDACT / BLOCK` 三态处置，
内容全程不出 VPC。

它和方案二的根本区别是**视角对调**：方案二是**透明 MITM**（客户端不改配置、只信任企业 CA，靠冒充
域名拿明文，能覆盖硬编码 provider 的 Kiro）；方案一是 **opt-in 网关**（客户端**必须能改 `base_url`**
才被审，因此覆盖不了 Kiro，但也**不碰 TLS 信任链、不伪造任何证书**）。两者的 DLP 引擎是**同一套**
（都 `import dlp.engine`，复用 `kiro-dlp-engine` 镜像），只是拦截点不同。**能改 `base_url` 就走方案一，
别做中间人。**

## 1. 为什么是「opt-in 网关」而非 MITM —— 三条设计约束

### 1.1 约束 A：能改 `base_url` 时，TLS 终止是最干净的拿明文方式

内容审查只能发生在**能拿到明文的点**。拿明文有两条路：

| 路径 | 前提 | 代价 |
|---|---|---|
| **TLS 终止网关（方案一）** | 客户端**能改** `base_url` 指过来 | **零**——网关是流量的合法目的地，客户端自己发起 TLS 到网关，网关持自己的正牌证书 |
| 透明 MITM（方案二） | 客户端**不能改**（端点硬编码） | 有真实代价——必须自建企业 CA、伪造目标域证书、分发根证书、正式安全评审 |

只要客户端能改 `base_url`，就没有任何理由去做中间人：网关是流量**主动交付**的终点，不冒充任何人，
不需要客户端安装企业 CA，不触碰系统信任链，也就没有方案二那两个证书坑（链不完整 / Name
Constraints 自伤）与合规负担。**这是「能改就别 MITM」的物理基础。**

### 1.2 约束 B：LiteLLM 是既成的多模型网关，DLP 挂 guardrail 即可，不重造轮子

LiteLLM proxy 本就是「客户端改 `base_url` 指过来、由它统一转发到各家上游模型」的网关。它原生提供
`CustomGuardrail` 扩展点与 `pre_call` / `pre_mcp_call` 等 hook。方案一不自己写 HTTP 代理，而是把 DLP
做成一个 guardrail 插件（`dlp_guardrail.py`）挂进去——拦截点天然落在「明文 prompt 出网关前」和
「MCP 工具调用出网关前」，且能复用 LiteLLM 的虚拟 key、多上游、参数规整（`drop_params`）等能力。

### 1.3 约束 C：网关只能看见「过网关」的流量，通道级外带需 default-deny 兜底

opt-in 是双刃：客户端**主动**接入才被审，**没接入的客户端完全不过网关**。而且即便过了网关，内容
DLP 也只能看见「作为 prompt / MCP 参数」的明文。它**看不见**：

- agent 自主 `shell`（`git push` / `curl --data-binary @secret`）——秘密经通道离开，参数明文里没有；
- 变量解引用外发（`curl -H "Authorization: Bearer $TOKEN"`）——明文里只有 `$TOKEN` 字面；
- 专有源码/业务逻辑——无固定签名、无 PII、无高熵，L0–L3.5 召回 ≈ 0。

这些盲区不是内容引擎能补的，只能靠**出口层 default-deny 白名单**（命令白名单 / 出站域名 / git remote /
DB connection allowlist）兜底。方案一诚实地只覆盖「prompt 与 MCP 入参侧的确定性敏感数据」，其余靠
出口管控收口、靠 L4 异步告警提供事后可见性（见 §4、§8）。

**数据流（prompt 腿）**：客户端 → `gateway:4000/v1/chat/completions`（客户端自己终止 TLS 到网关）→
`async_pre_call_hook` 取 `data["messages"]` 全部 role 的字符串 content → 逐条 `engine.scan(...,
run_async_l4=False)` → `BLOCK` 抛 `HTTPException(400)`（请求不出网关）/ `REDACT` 就地替换 `messages[idx]
["content"]` 后放行 / `PASS` 原样 → 转发上游 Bedrock。放行面另投异步 L4 告警。

`inputs["tool_calls"][].function.arguments`（JSON 串按 `InjectionPoint.MCP` 扫）→ 同样三态；`REDACT` 时
只回写该 tool call 的 `arguments`。

## 3. 组件职责

### 3.1 LiteLLM proxy（`litellm` 容器，:4000）

- **TLS 终止 + 多上游网关**：客户端 `base_url` 指过来，它统一转发到上游模型（本轮上游 = Bedrock
  `qwen.qwen3-32b-v1:0` / `meta.llama3-1-8b-instruct-v1:0`，经实例 IAM 角色调用，**不落长期 AK/SK**）。
- `master_key: os.environ/LITELLM_MASTER_KEY`：admin key 从环境注入，用于签发虚拟 key、读日志/开销。
  **刻意不给默认值**（见 §6）。
- `drop_params: true`：上游不支持的参数静默丢弃，避免客户端参数差异打断转发。
- 挂两个 guardrail（`litellm_config.yaml`），`default_on: true`——默认对所有请求生效，不需客户端显式启用。

### 3.2 `CorpDLPGuardrail` 的两个 hook（`dlp_guardrail.py`，方案一的大脑）

一个类，经 `litellm_config.yaml` 以两种 mode 注册，覆盖两个拦截点：

| guardrail 名 | mode | 进入方法 | 扫什么 | 注入点 |
|---|---|---|---|---|
| `corp-dlp-pre` | `pre_call` | `async_pre_call_hook` | `messages` 全 role 字符串 content | `PROMPT`；role==`tool` 的消息 → `FLOWBACK` |
| `corp-dlp-mcp` | `pre_mcp_call` | `apply_guardrail` | `tool_calls[].function.arguments`（JSON 串） | `MCP` |

- **`async_pre_call_hook`**（hook 1，扫出站 prompt + flowback 回流）：
  - `_extract_message_texts` 取所有 role 的字符串 content（含多模态分段里的 `text` 段）；**关键：连
    `role=="tool"` 的消息也扫**——工具返回值会回流进下一轮上下文发往云端，这是最易被忽视的整层盲区
    （03 文档套件 5）。
  - 逐条 `await asyncio.to_thread(_engine.scan, text, injection_point=ip, run_async_l4=False,
    session_window=window or None)`——引擎是同步 CPU/HTTP 代码，放线程池执行避免阻塞事件循环；
    `session_window` 传同请求内此前消息，覆盖跨消息拆分密钥拼接（EVA-03）。
  - `BLOCK` → `raise HTTPException(status_code=400, detail={"error":"blocked_by_corp_dlp", ...})`，
    请求**不出网关**；`REDACT` → `messages[idx]["content"] = result.redacted_text` 就地替换后放行；
    `PASS` → 原样。
  - 放行面 `asyncio.create_task(_l4_async_alert(full_text))`——L4 语义审查投异步队列（此处简化为
    fire-and-forget，生产应为持久队列），**绝不进同步裁决**。
- **`apply_guardrail`**（hook 2，统一 guardrail 通道）：litellm main-latest 一旦类里定义了
  `apply_guardrail`，`pre_call` 与 `pre_mcp_call` 都走它。
  - 新契约：`inputs` 为 dict，`texts[]` 按 `PROMPT` 扫、`tool_calls[]` 的 `function.arguments` 解析成
    `{"tool":name,"arguments":{...}}` 按 `MCP` 扫；`REDACT` 就地回写。
  - 旧契约（单段 `text`，MCP 直连）仍兼容，按 `MCP` 扫。
  - `BLOCK` 统一走 `_raise_if_block`（同样 `HTTPException(400)` + `blocked_by_corp_dlp`）。
- **`scan_mcp_call(call)`**：直连口，供离线/阶段2 验证构造好的 MCP dict（含 `field_path` 命中定位）。
- **指标**：每次裁决 `_record()` 写 `DLP_METRICS_PATH`（默认 `/tmp/dlp_gateway_metrics.jsonl`）一行
  `{ts, kind, verdict, top_layer, latency_ms}`——阶段3 压测/阶段2 verdict 分布对账读它。

### 3.3 共享 DLP 引擎（`dlp.engine`，与方案二同一套）

- 网关容器 volume 挂 `../engine/dlp` 到 `/app/dlp`（**纯 stdlib 源码包，无需 pip 安装**），guardrail
  直接 `from dlp.engine import DLPEngine, EngineConfig`。
- 分层：`L0 正则/词表 → L1 detect-secrets/gitleaks → L2 高熵+语境 → L3 Presidio(PII) → L3.5 术语表/EDM`；
  **L4 语义 LLM 永远异步**。同步链路 `run_async_l4=False`——`top_layer=L4` 出现在同步 verdict 里就是
  「误触 L4」的红线告警。
- 聚合语义（与 SPEC §2 一致）：任一 `BLOCK` → BLOCK；否则任一 `REDACT` → REDACT；否则 PASS。
  `top_layer` = 命中里层级最低（最先确定性）的那层。
- **`use_bedrock_l4`** 由环境开关 `DLP_L4_BEDROCK`（默认 `0`）控制，仅影响**异步告警路径**的 L4 后端。

### 3.4 L3 Presidio analyzer（`presidio-analyzer` 容器，内网 :5002）

- zh 增强镜像（`Dockerfile.presidio-zh`）= 官方镜像 + `zh_core_web_sm` + en/zh 双语 NLP 配置
  （`en_core_web_lg + zh_core_web_sm`）。仅内网互通，不对宿主暴露。
- L3 经 HTTP 调它做 PII NER（PERSON/EMAIL/PHONE/LOCATION/CREDIT_CARD…）。**这是唯一的重量级依赖，
  也是长文本高并发下的性能热点**（04 文档 §3、03 §8.3：单核打满）。

### 3.5 L4 语义（异步告警，本轮 Bedrock 标定）

- `_l4_async_alert` 经 `asyncio.to_thread` 调 `l4_semantic.analyze(text, use_bedrock=_USE_BEDROCK_L4,
  model_key="main")`，命中产 `category / confidence / model / rationale` 告警，`_record("l4_alert", ...)`
  落盘 + 进 litellm 日志。**永不阻断、永不改同步 verdict**（SPEC §5-L4 铁律）。
- 本轮后端用 Bedrock（Qwen3-32B 主 / Llama-3.1-8B 对照）**仅做功能可行性标定**——见 §6 红线。

## 4. 三个注入点（方案一覆盖面的准确边界）

方案一在网关内**同步**覆盖三个注入点，对应引擎的 `InjectionPoint`：

| 注入点 | 来源 | hook | 典型威胁 | 覆盖 |
|---|---|---|---|---|
| **PROMPT** | 用户消息 / 代码上下文（`role != tool`） | `pre_call` | prompt 里明文贴密钥/PII/内部代号 | ✅ 同步 block/redact |
| **FLOWBACK** | 工具返回值回流（`role == tool` 的消息） | `pre_call` | `read_file` 读回 `.env` → 注入下一轮上下文发往云端 | ✅ 同步（入参与返回值两侧都扫） |
| **MCP** | MCP 工具调用参数（`tool_calls[].function.arguments`） | `pre_mcp_call` | `write_file` content 硬编码 AKIA、`http_request` headers.Authorization | ✅ 同步 block/redact |

**不覆盖（结构性，见 §8）**：通道级外带（shell/git/http-body/DB，秘密不在参数明文里）→ 出口
default-deny 兜底；专有源码/业务逻辑 → 仅 L4 异步告警，同步必 pass。

## 5. fail 语义 —— 同步阻断链路只放确定性、亚秒可解的层

方案一的 fail 取向与方案二一致（安全侧优先），但表现形式不同（网关是同进程调用，不是跨主机 HTTP）：

| 情形 | 处置 | 理由 |
|---|---|---|
| L0–L3.5 命中 BLOCK | `HTTPException(400)`，请求**不出网关** | 确定性层裁决，硬阻断 |
| L0–L3.5 命中 REDACT | 就地替换文本后放行（HTTP 200） | 脱敏放行，保留可用性 |
| L4 语义（秒级不定、非确定、可被 prompt 注入） | **永不进同步裁决**，只投异步告警 | 延迟不可控 + 非确定 → 接入同步会拖垮网关且引入不确定阻断 |
| 指标写盘失败 | `except OSError: pass` | 指标是旁路，**绝不影响主链路** |
| L4 异步链路异常 | `except Exception` 只记录 | 告警链路故障**绝不影响主链路** |

**核心不变量**：同步阻断链路**只放 L0–L3.5**（确定性、亚秒）；L4 只做异步告警。这是「网关不因 DLP 变慢/
变脆」的设计底线——03 §8.3 实测短文本 DLP 净成本 c1 下约 45ms，L4 开启时同步 verdict 污染 = 0。

## 6. 安全红线（不可协商）

> 这些是方案一运行期间**任何时候都不能破坏**的不变量，破坏即停止/回滚。

1. **L4 语义 LLM 生产必须本地/VPC-only**：用第三方/云 LLM 审查外发内容 = **第二条泄漏通道**。本轮用
   Bedrock（us-west-2）**仅做功能可行性验证**，标定为**非红线合规**——数据离开了本 VPC，**不得作为
   生产配置**，报告必须显式写明；生产 L4 须自建（g6 vLLM 或客户 VPC GPU）。跑完必须还原
   `DLP_L4_BEDROCK=0`（`host_stage4_l4.sh` 内置还原步骤）。
2. **同步腿绝不触 L4**：`run_async_l4=False` 是硬编码；`top_layer=L4` 出现在同步 verdict 里 = 红线告警。
   L4 语义永远异步。
3. **内容 DLP 是尽力检测（best-effort detection），不是硬预防（hard prevention）**：扫过 ≠ 不泄漏；
   系统性漏检新写源码/业务逻辑（套件 6）。报告不得以「扫过」表述为「不泄漏」。
4. **通道级外带绕过一切内容扫描**：shell exec / git push / http body / DB 连接必须靠**命令白名单 +
   出站域名/remote 白名单（default-deny）**兜底，而非内容引擎（套件 4）。
5. **`LITELLM_MASTER_KEY` 不留默认值**：compose 里刻意用 `:?` 而非 `:-`——默认值会静默成为网关 admin
   key（可签发虚拟 key、读全部日志/开销）。启动前必须 `export LITELLM_MASTER_KEY="sk-$(openssl rand
   -hex 24)"`。
6. **不伪造证书、不碰 TLS 信任链**：方案一是 opt-in TLS 终止网关，**不是 MITM**——不需要、也绝不自建
   企业 CA 或伪造上游域证书（那是方案二的活）。
7. **上游凭证经实例 IAM 角色，不落长期 AK/SK**：Bedrock 调用经 IMDS 取临时凭证（hop-limit=2 容器内
   可取），实例上**不复制**长期 access key。
8. **绝不 `NODE_TLS_REJECT_UNAUTHORIZED=0` / `rejectUnauthorized:false`**：客户端到网关的 TLS 校验绝不
   禁用绕过（与方案二共守此律）。
9. **响应绝不外泄原始敏感子串**：`BLOCK` 的 `detail.rules` 只回规则名（最多 10 条），**不回命中的原文**；
   指标 jsonl 只记 `verdict/top_layer/latency`，不记明文。

## 7. 与方案二的对比

| 维度 | 方案一（LiteLLM opt-in 网关，本文） | 方案二（选择性 bump MITM） |
|---|---|---|
| 拦截点 | LiteLLM 终止网关（`base_url` 重定向） | nginx + mitmproxy 透明 MITM |
| 客户端改动 | **必须改 `base_url`** | 只需信任企业 root CA，**无需改配置** |
| **能否覆盖 Kiro** | ❌ Kiro 硬编码 provider、不能改 base_url | ✅ 透明拦截，能覆盖 |
| 覆盖范围 | 所有主动接入网关的 agent/SDK | 仅 Kiro 推理腿（选择性 bump） |
| 明文获取 | TLS 终止（合法终点，网关持正牌证书） | 选择性 bump（冒充 `runtime.*.kiro.dev`） |
| 企业 CA | **不需要** | 必须自建三级 CA + 分发根证书（两个证书坑） |
| DLP 引擎 | **同一套** `kiro-dlp-engine`（`import dlp.engine`） | **同一套**（复用，只是拦截点不同） |
| TLS 风险 | 无（不解密，客户端自己终止到网关） | 有（明文集中在一台 EC2，靠 CA 三级链 + NC + 硬化收敛） |
| 合规负担 | 低（opt-in，用户知情） | 高（需正式安全评审 + 员工告知 + CA 分发） |
| 部署形态 | 网关容器（litellm + 引擎 + presidio） | 独立 EC2（nginx + mitmproxy + systemd） |
| 定位 | 治「可配 base_url 的自研 agent」 | 治「硬编码 provider 的 Kiro」 |

**互补关系**：两者不是替代，是**分层**。第 0 层永远是 opt-out（IdC 企业版合同）+ `.kiroignore` +
default-deny 出口白名单 + prompt logging（不碰 TLS）。方案一在「客户端可配 base_url」时是**最干净的
内容审查层**；方案二只在「硬编码 provider 且外发前必须同步硬阻断」是硬需求时，作为有真实代价的补充层。
**能改 `base_url` 就走方案一，别做中间人。**

  main 4/4 且同步 verdict 污染 0。
- **未做/遗留（诚实清单，不得以「扫过」表述为「不泄漏」）**：
  1. **tool_result 回流**：已 hook（FLOWBACK），但这依赖客户端把工具返回值作为 `role=tool` 消息发来；
     绕过消息通道的回流不覆盖。
  2. **通道级外带**：纯内容 DLP 对 shell/git/http-body/DB 必漏，只能靠 default-deny 通道白名单（套件 4）。
  3. **专有源码/业务逻辑**：L0–L3.5 召回 ≈ 0，仅 L4 异步——**内容已出境后才可能事后告警**（套件 6）。

     ——**部署配置问题（须多 worker 扩容），非架构缺陷**（03 §8.3）。
