## 0. 测试目标与红线(逐条固化,报告须原样引用)

**目标**:验证方案一(LiteLLM opt-in 网关 → `async_pre_call_hook` 扫 prompt → `pre_mcp_call` 扫 MCP 工具参数 → DLP 分层引擎 L0–L4 → VPC/本地 LLM 承载 L4 语义)在 aws-env 的**功能可行性**与**性能可接受性**。

**红线(不可违背,写进报告)**:

1. **L4 语义 LLM 生产必须本地/VPC-only**。用第三方/云 LLM 审查外发内容 = 第二条泄漏通道。**本轮用 Bedrock(us-west-2)仅做"功能可行性验证",标定为非红线合规**:数据离开了本 VPC 边界,**不得作为生产配置**,报告必须显式写明这一点;生产 L4 仍须自建(g6 或客户 VPC GPU)。
2. **内容 DLP 是尽力检测(best-effort detection),不是硬预防(hard prevention)**。扫过 ≠ 不泄漏;**系统性漏检新源码/业务逻辑**(见套件 6)。
3. **SNI 透传不解密**。方案一是 opt-in TLS 终止网关(客户端主动改 `base_url`),**不是 MITM**,不需要伪造证书/CA。
4. **通道级外带(shell exec / git push / http body / DB 连接)绕过一切内容扫描**。这类必须靠**命令白名单 + 出站域名/remote 白名单(default-deny)**兜底,而非内容引擎(见套件 4)。
5. **不伪造实测数字**;测试预言 ≠ 实测。

## 2. DLP 分层引擎实现建议(同步/异步放置 + 100ms/100token 约束)

**同步阻断链路只放确定性、亚秒可解的层(L0–L3.5)**;**L4 LLM 只做异步告警,永不同步硬阻断**(延迟不可控、非确定、可被 prompt 注入)。

| 层 | 技术 | 目标延迟 | 同步/异步 | 命中动作 | 关键实现点 |
|---|---|---|---|---|---|
| **L0** | 正则/词表 | 亚毫秒 | 同步 | block/redact | AWS/GCP key、身份证 18 位带 mod-11 校验、手机号段、邮箱;**扫描前 NFKC 归一化 + 全角→半角 + 去零宽/分隔符 + base64/hex/rot13 解码回扫**(套件 3 依赖) |
| **L1** | detect-secrets / gitleaks | ~10ms | 同步 | block | PEM 私钥头尾、`sk_live_`/`ghp_`/`AIza` 前缀、高熵;**PrivateKey vs CERTIFICATE 按 PEM 头精确区分**(FP-11) |
| **L2** | 高熵 + 语境 | ~10ms | 同步 | block/redact | Shannon 熵 **+ 语境关键词**(`password=`/`token:`)才判定;UUID/git SHA/base64 资源/lockfile integrity **无语境→放行**(套件 2 大量依赖) |
| **L3** | Presidio | **≤100ms/100token** | 同步 | redact | 官方 analyzer 容器(:5002)+ `BatchAnalyzerEngine`;**加载中文识别器**;信用卡 Luhn + 上下文降权(L3-11);自建 NER 用 `RemoteRecognizer` 移出关键路径;kiro-dlp 32G 直接跑 `en_core_web_lg` |
| **L3.5** | 术语表 / EDM | 亚毫秒 | 同步 | block/redact | Aho-Corasick;**词边界 + 大小写 + 专有短语约束**(避免撞普通英文词,FP-09/L35-13);ROI 最高层 |
| **L4** | 本地/VPC LLM | 秒级不定 | **异步告警** | **仅告警** | 输出 1-token 判定(敏感/不敏感 + 置信度),**不做长生成**;识别专有源码/业务逻辑;**绝不接入同步阻断路径** |

**Presidio 结构性局限**:对新源码/业务逻辑召回 ≈ 0(无固定签名、无训练 NER 类)→ 这是套件 6 的架构性缺口,不是可调参数解决的。

## 3. 本地/VPC LLM 选型建议(证据分级)

| 用途 | 推荐 | 理由 |
|---|---|---|
| 同步固定标签分类(如"是/否敏感") | **微调小编码器 DeBERTa-v3-base(184M)** | Pareto 占优:精度追平/超过 zero-shot ~10B LLM,延迟低 1–2 个数量级 |
| 非 LLM 本地 PII NER | **GLiNER** | 比 LLM 轻,可作 Presidio 的补充识别器 |
| **L4 语义(本轮·功能验证)** | **Bedrock Qwen3-32B**(主)+ **Llama-3.1-8B**(对照) | invoke 权限已确认;**仅功能验证标定** |
| **L4 语义(生产·守红线)** | 自建 **Qwen2.5-7B/14B** 或 **Llama-3.1-8B**(vLLM,g6 24G 足够;或 Ollama) | 数据不出 VPC |

### 套件 6 — 架构性缺口:专有源码/业务逻辑(同步必 pass,只验 L4 异步告警)

> **这是设计承认的缺口,不是 bug**。专有算法/权重/业务逻辑无固定签名、无 PII、无高熵 → L0–L3.5 召回 ≈ 0;仅 L4 语义能识别,而 L4 受硬约束**只能异步告警不能同步阻断**。因此同步链路**必然 pass**,内容已发往云端后才可能被事后发现。验证重点是:①同步不因 L4 卡住;②L4 异步告警在合理延迟内触发且带足够上下文供追溯;③本轮 L4 用 Bedrock **仅功能验证标定**。

## 7. 已知盲区与不可覆盖项(诚实边界,须进报告)

1. **tool_result 回流**:若未加回流 hook = 整层泄漏(套件 5 全组坐实)。
2. **通道级外带**:纯内容 DLP 对 shell/git/http-body/DB 必漏,只能靠 default-deny 通道白名单(套件 4)。
3. **专有源码/业务逻辑**:L0–L3.5 召回 ≈ 0,仅 L4 异步,同步必然 pass;意味着**内容已出境后才可能事后告警**(套件 6)。
4. **跨消息拆分**:需会话级滑窗;无状态逐条扫描会漏(EVA-03)。
5. **编码/混淆**:未做解码/NFKC 归一化则 base64/hex/rot13/全角/零宽全绕过(套件 3)。
6. **超长 payload 降级**:截断/采样/超时若静默 pass,则真凭证被淹没放行(EVA-12)。
7. **Kiro 无中国区**:代码必然出境;DLP 只减少、不能消除跨境传输——方案一是 opt-in,未 opt-in 的客户端完全不过网关。

> 结论口径:方案一能覆盖**确定性敏感数据(密钥/PII/内部代号)在 prompt 与 MCP 入参侧**的检测与脱敏,并对通道外带/专有源码给出**告警级**可见性;但它是**尽力检测而非硬预防**,以上 7 项须在报告如实列明,不得以"扫过"表述为"不泄漏"。

## 9. 性能测试方案(拦截成功率 + 压测下拦截延迟)

> **本节状态**:方法设计(§9.0~§9.8)+ **实测已完成**(§9.9~§9.13,2026-08-10 在 `kiro-dlp` 实例真跑)。§9.0~§9.8 是方法与判据门槛(**期望值**);§9.9 起是机器输出回填的**实测结果**,原始 k6/summary/`docker stats`/keep 对照探针归档在 `testing/results-2026-08-10/perf/`(含 `README.md` 导读)。**所有数字均取自实例机器输出,无手写**。
>
> **为什么要单开一节,阶段 3(§8.3)不够用**:§8.3 的 `bench_gateway.py` 只回答了一个问题——"干净流量开 DLP 比关 DLP 慢多少"。它有三处结构性缺口,决定它测不了本节要的两个指标:
> 1. **没有拦截向量**:三档 payload(CLEAN_SHORT / CLEAN_LONG / REDACT_PII)里没有一条 BLOCK 级凭证,所以"高并发下拦截还准不准"根本没被触碰;
> 2. **没有逐响应正确性断言**:它只统计 `status==200` 的延迟、把非 200 计 `errs`,而 BLOCK 的正确行为**就是** 400——在它眼里正确拦截和真故障无法区分;
> 3. **closed-loop 度量**:`ThreadPoolExecutor` 是"发一个等一个",系统一变慢线程自动降速,过载时的尾延迟被**少发请求**掩盖(见 §9.3 coordinated omission)。
>
> 所以本节不是给 §8.3 补几个数,而是换一套**面向拦截**的度量框架。

### 9.0 两个待测指标的精确定义

对标 **RFC 9411**(网络安全设备基准测试方法)的 *Security Effectiveness / Block Rate* 口径,把用户口语的"拦截成功率"和"拦截延迟"钉死为可测量、可判读的量:

| 指标 | 定义 | 为什么这么定义 |
|---|---|---|
| **拦截成功率(Block/Redact Rate)** | 在给定并发/到达率下,应被拦的攻击向量中**实际被正确处置**(BLOCK→400 短路 / REDACT→明文被遮蔽)的比例 | 借 RFC 9411 的 Security Effectiveness:效果必须在**有负载**时测,空载 100% 不代表满载 100%。分母是"注入的攻击数",分子是"客户端侧证实被正确处置数" |
| **误杀率(False Positive Rate under load)** | 在同等负载下,合法流量中被误 BLOCK/REDACT 的比例 | 拦截率和误杀率是一对**必须同时报的数**:只报拦截率可以靠"全拦"作弊。对标 §8.2 的"套件 2 = 0 误报基线",本节把它推到负载下复测 |
| **压测下拦截延迟** | **按处置路径分开**的端到端延迟分位数(p50/p95/p99/p999):① BLOCK 路径(网关内 400 短路,**不出网关**)② REDACT 路径(改写 + 转发上游)③ PASS 路径(纯放行) | 三条路径的代码路径和出网行为完全不同(BLOCK 不打上游、REDACT 要改 body),混在一起测出的分位数没有意义。BLOCK 路径延迟尤其关键——它是"坏内容被挡在门内"的耗时 |

> **一句话区分**:拦截**成功率**回答"高并发下还拦不拦得住";拦截**延迟**回答"拦这个动作本身要多久、尾部有多长"。二者都必须在**受控到达率**下测,且都要有**双数据源对账**(§9.6)。

### 9.1 三类工作负载(RFC 9411 风格,三种流量分开测)

把"拦截率"拆成三个互不污染的实验,避免一锅乱炖:

| 负载 | 组成 | 测什么 | 判据(期望) |
|---|---|---|---|
| **A · 纯攻击** | 100% BLOCK/REDACT 向量(见 §9.1.1) | 上限检出率:引擎在**打满但不排队**时的处置正确率 | BLOCK 向量 100%;REDACT 向量在 Presidio 健康时 100% |
| **B · 纯合法** | 100% 合法流量(§8.2 套件 2 扩展 + 长文本) | 负载下误杀率;吞吐上限(找到 95% 最大可检吞吐点) | 误杀率 = 0(与 §8.2 基线一致) |
| **C · 混合(主实验)** | 合法背景流(取 B 找到的 95% 最大吞吐)+ **定速注入**攻击向量(如每秒 5 条,与背景独立计数) | **负载下拦截率**:系统在接近吞吐上限、且被合法长文本喂到 Presidio 吃紧时,注入攻击是否仍被 100% 正确处置 | BLOCK 向量对过载**天然鲁棒**应保持 100%;REDACT-only 向量在 Presidio 过载时**要么脱敏成功、要么被强制 BLOCK**(fail-closed,§9.4),**绝不静默 PASS** —— 明文泄漏率必须 = 0 |

> 负载 C 的"定速注入"是关键设计:攻击向量以**独立于背景流的固定速率**打入,这样即使背景流把系统压到长尾,每一条攻击的处置结果都能被单独对账(§9.6),不会被背景流的统计淹没。

#### 9.1.1 攻击向量必须分两类,对账才有分辨率

现有向量库(§4 套件 + `fixtures_layers/`)已够用,但压测**必须显式区分**两类,否则测不出 L3 过载下的处置行为:

- **本地层裁决类(对 Presidio 过载鲁棒)**:AWS/GCP 密钥、PEM、Stripe/GitHub/OpenAI/Slack token、JWT、高熵串、身份证/手机号/邮箱正则、术语表/工单号/公司域名。由 **L0/L1/L2/L3.5** 判决,**不依赖 Presidio**。预期:无论 Presidio 多忙,这些 100% 被处置。
- **仅 L3(Presidio NER)可检类**:裸人名(PERSON)、裸地名(LOCATION)、信用卡(CREDIT_CARD)、IP——**不带**任何 L0/L1/L2/L3.5 特征前缀。**只有 Presidio 在线且不超预算才检得出**。这一类是 fail-closed 行为的**探针**:Presidio 过载时引擎跳过 L3、在 `notes` 写降级 marker,网关据此(规格 D4)**强制 BLOCK**——因此这类向量在过载下的正确结局是 **400 forced_block=l3_unavailable**,而非静默 PASS。

> 对账分辨率来自这个划分:把两类向量在同一过载条件下的处置率并排放,**本地类维持正常处置、L3 类从 REDACT/200 转为 forced-BLOCK/400 但明文泄漏率仍为 0**,就精确坐实了"L3 降级被网关 fail-closed 兜住",而不是笼统的"高并发不准了"。对照实验(`DLP_L3_UNAVAILABLE_ACTION=keep`)下 L3 类会退回静默 PASS 明文泄漏,两者并排即量化 fail-closed 的收益。

### 9.2 压测必须 open-loop(constant-arrival-rate),不能沿用 closed-loop

- **coordinated omission(Gil Tene)**:closed-loop 压测器(每 worker 发一个、收到再发下一个,如现有 `bench_gateway.py`)在系统变慢时会**自动降低发送速率**——一条 5s 的慢请求期间,这个 worker 不会再发新请求,于是"本该在这 5s 内到达却被 worker 自己憋住没发"的请求从未被计时。结果:**过载时的尾延迟被系统性低估**,p99 看着很美。
- **修法 = open-loop**:按**固定到达率**注入(不管系统跟不跟得上),排队就让它在延迟里体现出来。**k6 的 `constant-arrival-rate` executor** 正是 open-loop——按 `rate` 启动 iteration、预分配 VU,VU 不够时报 `dropped_iterations`(这本身就是过载信号)。
- **工具选型**:**k6** 首选(open-loop 原生、HDR 直方图给 p99/p999、脚本里能对每条响应做 `check()` 断言→天然满足 §9.6 客户端侧对账)。现有 `bench_gateway.py` 保留作 closed-loop 对照(测"单请求净成本"仍有效),但**负载下的拦截率/尾延迟以 k6 为准**。

```javascript
// 骨架示意(非最终脚本):负载 C 的攻击注入 scenario
export const options = {
  scenarios: {
    background_legal: { executor: 'constant-arrival-rate',
      rate: /*待回填:B 实验得出的 95% 最大可检吞吐*/, timeUnit: '1s',
      duration: '5m', preAllocatedVUs: 200 },
    injected_attacks: { executor: 'constant-arrival-rate',
      rate: 5, timeUnit: '1s', duration: '5m', preAllocatedVUs: 50,
      exec: 'attack' },   // 每条断言 400(BLOCK) 或 遮蔽(REDACT)
  },
};
```

### 9.3 隔离 guardrail 成本:mock 掉上游 LLM

要测的是**网关 + DLP 引擎**的开销,不是上游模型的生成延迟。必须把上游 RTT 从测量里剔除,三法任选(推荐前两者):

1. **fake OpenAI 兼容端点**(推荐):`litellm_config.yaml` 增一个 `model_name` → `litellm_params: {model: openai/any, api_base: http://127.0.0.1:<port>}`,`<port>` 起一个返回固定 chat/completions JSON 的极简服务(nginx `return` 或 20 行 Flask)。上游 RTT≈0,压测延迟 = 纯 guardrail + 网关开销。**REDACT 路径要走完整个改写+转发,所以必须有这个假上游**(不能只靠 mock_response)。
2. **LiteLLM `mock_response`**:请求带 `mock_response` 或 config 设定,LiteLLM 直接返回不打上游。**已核查的坑**:mock 响应的 `usage` 是**硬编码**(prompt/completion/total ≈ 10/20/30),不是 null——所以基于 TPM 的路由/限流会被**压平**而非失效,**别用 mock_response 去测 TPM 限流行为**;测 guardrail 延迟则无影响。
3. 本机起 vLLM/llama.cpp mock:最真实但引入自身开销,仅在需要"带真实生成延迟的端到端"时用。

> BLOCK 路径本就 400 短路、**从不打上游**,故它的延迟对是否 mock 上游不敏感;但 PASS/REDACT 必须 mock,否则测的是上游而非网关。

### 9.4 核心实验:L3 过载下的 fail-closed 验证(与 §5「降级安全」判据对齐)

这是本节**最重要**的一个实验,也是新增性能测试相对旧压测的最大增量:在 Presidio 被压到过载、L3 被跳过时,**量化网关是否真正 fail-closed**(强制 BLOCK / 脱敏成功,而非静默 PASS)。

- **机制回顾(源码级)**:引擎 `engine.py` 的 `_aggregate()` **只看每个 `Hit.action`、不读 `l3_state`**——L3 Presidio **缺席 / partial / 超 `l3_budget_s`(6.0s)墙钟预算**时,截断只写 `notes`("L3 skipped …")并置 `l3_state["incomplete"]`,**`scan()` 返回的 verdict 结构上不会因此升 BLOCK**。fail-closed 的补偿责任在**消费者**。
- **网关现已 fail-closed(规格 D4,本轮改造)**:`CorpDLPGuardrail._dispose()` 经 `_forced_block_reason()` **扫 `result.notes`**:命中 L3 降级 marker(`analyzer 不可达 / 部分语言失败 / L3 skipped`)→ **强制 BLOCK(400,`forced_block=l3_unavailable`)**,由 `DLP_L3_UNAVAILABLE_ACTION` 控制(默认 `block`,仅显式 `keep` 退回旧 fail-open);命中「REDACT 未生效」→ 恒强制 BLOCK(`redaction_ineffective`)。语义与方案二 `server.py` 逐字一致——**同一个引擎,两方案现都 fail-closed**,差别只在拦截点。
- **与判据对齐**:§5 明写"降级时应 **fail-closed 或告警,不得静默 pass**"。改造前方案一网关只读 verdict、不读 notes,与该判据冲突(fail-open);改造后网关读 notes 强制升级,**与判据及方案二对齐**。本实验就是在真机负载下**量化这条 fail-closed 通道是否闭合**。
- **验证实验设计**:
  1. 用**长文本合法流**(~2000 token,§8.3 已证会把单副本 Presidio 单核打满)做背景,把 Presidio 压到超 `l3_budget_s`;
  2. 定速注入**两类攻击**(§9.1.1):本地层类 + 仅 L3 类;
  3. 观测:**本地层类处置率应稳定 100%**(L0/L1 不依赖 Presidio);**仅 L3 类在过载下应表现为「脱敏成功(200,明文遮蔽)或强制 BLOCK(400,`forced_block=l3_unavailable`)」二者之一,明文泄漏率 = 0**;
  4. 交叉验证:客户端侧 L3 类**无一返回 200 且明文 PII 未遮蔽** ⇔ metrics jsonl 对应记录 `verdict=block` 且 `forced_block=l3_unavailable`(或 `redaction_ineffective`) ⇔ 引擎日志/ notes 出现 "L3 skipped"。三源一致即坐实 fail-closed 生效;
  5. **对照组(可选,量化收益)**:同一负载下 `export DLP_L3_UNAVAILABLE_ACTION=keep` 重跑,L3 类会退回静默 PASS(明文泄漏率 > 0)——两组并排即量化 fail-closed 相对旧 fail-open 的收益。
- **判据**:L3-only 向量在过载下的**明文泄漏率必须 = 0**(要么脱敏成功、要么 400 强制拦截)。**若出现泄漏 > 0**,说明 fail-closed 通道未闭合(如 marker 未命中、开关被误设 `keep`),报告须如实标注并定位;`keep` 对照组的泄漏率则作为"旧 fail-open 边界"如实记录。

### 9.5 单机合并部署的绑核纪律

`kiro-dlp` 单机 8 vCPU 上同时跑 litellm / dlp-engine / presidio,再叠一个压测负载生成器会**互相抢核**,污染延迟测量(§8.3 阶段 3 已吃过"孤儿容器抢核"的亏,见 §8.3 与 04 踩坑实录)。

- **首选**:k6 **放到另一台实例**发压,`kiro-dlp` 只承载被测服务——彻底隔离负载生成器的 CPU。
- **次选**(仍单机):`taskset` 把被测三容器绑到固定核集合(如 0–5)、k6 绑到另一组(6–7),`docker stats` + `mpstat -P ALL` 拆分每容器/每核占用,确保瓶颈归因干净。
- 每轮压测都记快照:`docker stats` 三容器 CPU/内存 + Presidio worker 数 + `l3_budget_s`/`l3_concurrency` 配置值(它们直接决定 L3 被跳过的频率,即 fail-closed 强制 BLOCK 的触发窗口大小)。

### 9.6 双数据源对账(客户端断言 ⊕ 网关 metrics)

拦截率**不能只信一侧**,两个数据源交叉:

- **源 1 · 客户端侧(k6)**:每条注入攻击在 k6 脚本里 `check()`——BLOCK 期望 HTTP 400 且 body `error=="blocked_by_corp_dlp"`;REDACT 期望 200 且响应里**原始 PII 明文消失**。这是"处置是否正确"的**权威判据**。
- **源 2 · 网关 metrics jsonl**:`dlp_guardrail._record()` 写 `/tmp/dlp_gateway_metrics.jsonl`,每条 `{ts, kind, verdict, top_layer, latency_ms}`。用于:① 交叉核对客户端计数;② 提供**网关内部视角的延迟**(与客户端端到端延迟做差 = 网络+LiteLLM 框架开销);③ 看 `top_layer` 分布确认处置由哪层做出。
- **已知对账限制**:metrics jsonl **没有 request id**,无法与客户端请求逐条配对,只能**按时间窗 + verdict 计数**对账(客户端在窗口内发了 N 条 BLOCK 攻击 ⇔ 同窗口 metrics 应有 N 条 `verdict=BLOCK`)。计数一致即认为对齐;若要逐条配对,需给 `_record()` 加透传的关联 id(列为可选改进,不阻塞本轮)。

### 9.8 诚实边界(本节须进报告)

1. **§9.0~§9.8 门槛是期望值**:表中门槛为设计期望,实测可能推翻;§9.9 起的所有数字均经 `kiro-dlp` 真跑、取自机器输出,无手写。
2. **网关本轮已由 fail-open 改为 fail-closed**(规格 D4):`_dispose` 读 `notes` 对 L3 降级强制 BLOCK。实验 D 的作用是**在真机负载下验证这条通道闭合**(L3-only 明文泄漏率=0);旧 fail-open 仅在 `DLP_L3_UNAVAILABLE_ACTION=keep` 对照组下复现,用于量化收益,**非生产配置**。改造前的 fail-open 是**已坐实的机制事实**(引擎 L3 超预算不改 verdict + 改造前网关只读 verdict),非猜测。
3. **metrics 对账是计数级、非逐条**(§9.6 限制),报告不得声称"每条请求都双向核对"。
4. **单机测量含合并部署噪声**:即便绑核,8c 上四类进程共存的干扰无法完全消除;长文本吞吐上限强依赖 Presidio 副本数,**扩容后须复测**(承接 §8.6 遗留①)。
5. **假上游 ≠ 真实上游延迟**:本节延迟是**网关侧净成本**,不含真实模型生成时间;端到端用户感知延迟需另计上游 RTT。

### 9.13 fail-closed 收益量化:停 Presidio + keep 对照(§9.4-5)

marker→强制 BLOCK 通道需在 **L3 干净不可达**(而非排队阻塞)时才触发。停掉 presidio-analyzer 制造该条件,用同一 l3only probe(信用卡 `4539578763621486`,健康时 top=L3)对比默认 fail-closed 与 `keep` 旧 fail-open:

| 组别 | `DLP_L3_UNAVAILABLE_ACTION` | HTTP | verdict | forced_block | 明文是否到上游 echo |
|---|---|---|---|---|---|
| **生产默认(fail-closed)** | `block`(默认) | **400** | block | **`l3_unavailable`** | **否** |
| **对照(复现旧 fail-open,非生产)** | `keep` | 200 | pass | — | **是**(卡号 `4539578763621486` 明文出现在 echo 响应) |

> **同一请求、同一 L3 不可达故障,处置相反**:默认 `block` 组强制拦截、卡号不出网关(泄漏=0);`keep` 组静默放行、卡号明文到达上游。这直接量化本轮 fail-closed 改造的收益 —— **L3-only 敏感数据在 Presidio 宕机时的明文泄漏率 1 → 0**。`keep` 仅作收益量化/对照,**非生产配置**(生产默认即 `block`)。
>
> 时序坑(已归档):litellm 经 compose recreate 会因 `depends_on: presidio(service_healthy)` 把 presidio 一并带起,故 keep 组必须**在 recreate 之后再停 presidio**,否则探测时 L3 已自愈、测不到 fail-open。

**实测遗留(承接 §8.6,不改结论)**:

1. **单副本 Presidio 是吞吐天花板**:合法短流拐点 ~80 /s、封顶 ~84 /s;长文本更早触顶。扩容 Presidio 副本 / 提 `l3_concurrency` 后须复测(§8.6 遗留①)。
2. **过载降级有两种机制,本轮只自然触发了"排队阻塞"**:实验 D 未走到"引擎 L3 预算跳过 + notes marker"路径(`forced_block=0`),该 marker 通道的闭合由 §8.2.1 停 Presidio 专项 + §9.13 keep 对照坐实。若要在负载态直接触发 marker,需给 Presidio 设更激进的 `l3_budget_s` 上限或注入慢响应,列为后续增强。
