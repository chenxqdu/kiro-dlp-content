# 企业 AI 数据防泄漏解决方案

## 分层纵深，把 AI 工具的数据外泄风险讲清楚、收得住

> **一句话价值主张**：以分层纵深防护，系统性降低源码、密钥、业务逻辑与客户 PII 外泄到云端 LLM 的风险。
>
> 我们不承诺「零泄漏」。我们提供的是「opt-in 统一网关」为首选、「透明拦截」为谨慎补充、「default-deny 出口」为结构性兜底的多层体系，并对每一层的覆盖边界做**诚实标定**，而非营销式承诺。

---

## 一、你正在面对的真实场景

这些不是假设，而是每一家已经在用 AI 工具的公司此刻正在发生的事。

| 场景 | 谁在做 | 泄漏的是什么 | 传统 DLP 为什么拦不住 |
|---|---|---|---|
| 把报错堆栈＋源码片段贴进 AI 助手求解 | 平台／业务研发 | 源码、内部逻辑、内网地址 | 走标准 HTTPS 加密信道，出口网关只看到一个到大模型域名的加密连接，看不到明文 |
| 用闭源 AI 编码工具（如 AWS Kiro）写代码 | 全体开发者 | 为了补全，整个代码库上下文被自动打包进推理流出境 | 推理端点硬编码，无法重定向到自有网关 |
| Agent 自主调用 shell／外部 API／扩展回传 | 自动化 Agent | 密钥、业务数据、任意可达内容 | 不走可观测的推理接口，绕过一切内容审查 |

这些流量默认全部出境到海外云端大模型。你既不知道发了什么，也无法在发出前拦一道。

---

## 二、核心洞察：防护点由「客户端能否被重定向」决定

内容审查只能发生在**能拿到明文的点**。据此，客户端分两类，对应两条完全不同的路径：

```
                客户端能改 base_url 吗？
                        │
        ┌───────────────┴───────────────┐
       能                              不能
        │                                │
 自研 Agent／SDK／AI 应用          闭源商业工具（如 Kiro）
        │                                │
 方案一：LiteLLM 统一网关          方案二：Kiro 透明拦截
 （opt-in 终止，干净首选）        （TLS 终止 MITM，较重、有代价）
        │                                │
        └───────────────┬────────────────┘
                        │
     兜底：default-deny 出口白名单（根控制，先行部署）
```

> 图注：客户端类型 → 防护点决策树。唯一变量是「客户端的 LLM 端点能否被指向企业自有网关」。

| 客户端类型 | 能否改 `base_url` | 拿明文的方式 | 对应方案 | 代价 |
|---|---|---|---|---|
| 自研 Agent／SDK／AI 应用 | **能** | 客户端主动把流量交给网关（opt-in，客户端主动接入，合法端点） | **方案一：LiteLLM 统一网关** | 轻、干净、低风险 |
| 闭源商业工具（如 AWS Kiro） | **不能**（推理端点硬编码） | 只能在 TLS 终止代理处透明拦截（MITM，中间人解密） | **方案二：Kiro 透明拦截** | 重、有代价、须谨慎分层 |

关键区别：方案一里网关是**客户端自愿交付明文的合法终点**，无需伪造证书、无需分发企业 CA、不破坏 TLS 信任；方案二必须终止 TLS，等于为全体开发者的加密信道背书，是有真实代价的补充层。一句话——**能改 `base_url` 就别做中间人；不能改，中间人也只是补充层而非核心。**

## 三、方案全景

> 图注（架构图占位）：整体数据流——可配置客户端 → LiteLLM 网关；闭源工具 → 选择性 bump 代理 → DLP 分层引擎 → 上游模型；全部出站流量统一收敛到 default-deny 出口白名单。

- **方案一 · LiteLLM 统一网关**：面向能配置 `base_url` 的自研 AI 应用。作为 opt-in 的 TLS 终止网关，在 prompt 送往上游模型前做内容审查，并对 MCP 工具调用参数做 guardrail 审查，命中即脱敏改写或阻断。单台 EC2 + Docker 即可起。
- **方案二 · Kiro 透明拦截**：面向推理端点硬编码、无法重定向的闭源工具。在 TLS 终止代理处透明拦截推理流，送入 DLP 后阻断或放行；配合端点侧 `.kiroignore` / MDM 从源头排除敏感文件。这一层还有两种部署形态可选——**跑在共享网关**（统一强制、统一留痕，但是全公司级明文单点）或**跑在每台开发机本地**（爆炸半径小，但依赖端侧可信、集中强制力弱）。两种形态的取舍见下方决策清单的 C / D。
- **贯穿控制 · default-deny 出口白名单**：default-deny 即「默认拒绝、仅白名单放行」。它不碰 TLS、不新建明文枢纽，却是唯一能兜住「拦截看不见的盲区」的结构性根控制，应优先部署。

## 四、能力矩阵

| 防护维度 | 方案一：LiteLLM 网关 | 方案二：Kiro 透明拦截 | default-deny 出口白名单 |
|---|---|---|---|
| 适用客户端 | 可配 `base_url` 的自研 Agent／SDK | 闭源硬编码工具（Kiro） | 全部出站流量 |
| 是否终止 TLS／需企业 CA | ✗（opt-in 合法明文） | ✓（MITM，需 CA） | ✗ |
| prompt 内容审查 | 支持 | 支持（仅推理流） | 不涉及（只看目的地） |
| MCP 工具调用审查 | 支持（`pre_mcp_call`） | 部分（仅 remote MCP） | 不涉及 |
| 原生工具／自主 shell／stdio MCP | 不适用 | 不支持（盲区） | 兜底（拦未知目的地） |
| 部署重量 | 轻（单 EC2 + Docker） | 重（选择性 bump + CA + 评审） | 轻 |
| 主要风险 | 低 | 全司明文单点、CA 攻击面、监听定性 | 低 |
| 建议失败模式 | fail-open／fail-closed 可选 | 降级透传 + 告警 | default-deny |

## 五、适用与不适用场景

**适用**

- 想在员工用大模型／AI 编码工具时降低机密外泄风险，并对管理层给出有边界、可解释的防护标定。
- 已有自研 Agent／SDK，希望统一 DLP 与 MCP 工具调用审查（方案一，首选）。
- 已部署 SNI 透传代理，希望在监管硬性要求「出境前同步阻断」的窄场景下，受控引入透明拦截（方案二，补充层）。

**不适用／须先对齐预期**

- 期望「扫描通过 = 无泄漏」的硬保证——内容型 DLP 是 best-effort 检知，不是硬预防，对新写的源码、改写后的业务逻辑会系统性漏检。
- 期望消除跨境——Kiro 无中国区，代码必然出境，DLP 只能降低、不能消除。
- 期望静默上线——终止 TLS／注入 CA 必须经安全评审、告知使用者并取得同意。
- 用第三方 LLM 做外发内容审查——那是二次泄漏。语义审查所用的 LLM 必须本地／VPC-only。

## 六、诚实标定（这一节请管理层务必读）

- **分层而非银弹**：任何单点都不是完整防护，正确姿势是多层纵深。
- **内容型 DLP 是 best-effort 检知，不是硬预防**：一段内容是否属于本公司机密、是否该出境，往往无法仅从内容本身判定——它取决于业务归属与上下文。对已登记的指纹（密钥／术语／EDM）强，对新写的源码、改写过的逻辑系统性漏检。**扫描通过 ≠ 无泄漏。**
- **数据驻留 ≠ 内容审查**：Kiro 无中国区，代码必然出境，DLP 只能降低、不能消除跨境。
- **MITM 有真实代价**：终止 TLS + 注入企业 CA，等于你为全体开发者的加密信道背书。它会形成全司明文单点、扩大 CA 攻击面，并可能被定性为监听。因此它只应作补充层，且绝不静默上线。
- **CA 分发不是「一个开关」**：Kiro 并非单一 TLS 栈，而是 3–4 条各自独立信任证书的栈（界面 Chromium、IDE 推理所在的 Node/Electron 扩展宿主、CLI 的 Rust 栈、CLI 推理子进程的 Bun 栈），信任机制彼此不同、需**分别下发并逐栈实测**——没有任何单一手段（如只设一个环境变量）能保证全覆盖。详见技术博客第七节。
- **default-deny 出口白名单是根控制**：它不碰 TLS、不新建明文枢纽，却是唯一能兜住上述盲区的结构性控制，应优先、先行部署。

## 七、决策清单：按你的真实威胁模型选路径

先定义四个可复用的控制手段：

- **A · 合同 + 事后可审计**：IdC 企业版合同性 opt-out（不训练／不留存）+ prompt logging 落自有 S3 + Macie／EventBridge 事后告警。不碰 TLS、不看内容。
- **B · 出口 + 扩展白名单**：现有 SNI 代理收紧为 default-deny 出口白名单 + IDE 扩展来源限制为内部白名单。不解密任何内容，是 agent 自主外发／扩展乱回传**唯一**兜得住的控制。
- **C · 客户端本机 MITM**：方案二的拦截逻辑跑在每台开发机本地，CA 只装这一台机器，爆炸半径最小，但依赖端侧可信。
- **D · 网关式选择性 MITM**：方案二的拦截逻辑跑在共享网关，统一强制、统一留痕，但是全公司级明文单点。

| 你的真实威胁模型 | 推荐路径 | 需要 MITM？ |
|---|---|---|
| 只担心内容被用于训练 | A 的 opt-out 部分 | 否 |
| 担心内容留在 AWS 侧、要可审计 | A（opt-out + prompt logging + Macie/CloudTrail） | 否 |
| 担心开发者误贴机密，接受事后近实时告警 | A + B | 否 |
| 担心 agent shell / MCP / 扩展乱外发 | B 的 default-deny 出口 + 扩展 registry（MITM 对此无效） | 否 |
| 内容离开边界前必须同步硬阻断 + 端侧可信 | A + B 打底，再加 **C** + 分层 DLP | 是（本机） |
| 同上但需集中强制、端侧不可信 | A + B 打底，再加 **D** + 分层 DLP | 是（网关） |
| 硬约束是「代码不能出境」 | 不用 Kiro / 换国产替代 | 不适用 |

**多数公司的多数威胁模型停在 A + B，走不到 MITM 这一步。** 只有落在表格下方两行——「同步硬阻断」不可退让——才需要认真考虑 C 或 D，且要先判断端侧可信度再二选一。

## 八、分层落地路线图

- **第 0 层（立即做，不碰 TLS，覆盖最广）**：可配置客户端上 LiteLLM 网关；闭源工具用 **A**（IdC 企业版合同性 opt-out + prompt logging + Macie/EventBridge 事后告警）+ MDM 下发 `.kiroignore` + **B**（现有 SNI 代理收紧为 default-deny 出口白名单 + 扩展白名单）。**多数威胁模型到此为止。**
- **第 1 层（仅当「出境前必须同步硬阻断」是硬需求）**：在第 0 层之上受控引入 **C 或 D**（按端侧可信度二选一，见上表），全部硬门槛到位；失败模式建议降级为透传 + 告警。
- **治理贯穿**：向管理层书面标定检测栈的覆盖边界；仪表盘明确标注「非泄漏保证」；不因上了检测栈而撤掉人工管控。

## 九、实测结果（两方案核心实测均已完成）

> 方案一已在 AWS us-west-2 真实环境（m7i.2xlarge 单机合并部署：LiteLLM 网关 + DLP 引擎 + Presidio 双语 NER + Bedrock L4 标定）完成五个阶段实测（2026-07-30 四阶段 + 2026-08-04/05 分层完备）；方案二已完成验证节点四层测试（2026-07-30）与**真实 Kiro 桌面端端到端**（2026-08-03）。**以下均为实测数字，完整矩阵与方法见《方案一-03-测试方案》§8 与《方案二-03-测试报告》。**

- **功能矩阵全绿**：56 条离线场景（金标准／误报基线／编码规避／通道外带／回流嵌套／L4 缺口六套件）**56/56 通过**；经 LiteLLM 网关端到端 **46/46 通过**。两条硬门达标：**该拦必拦漏拦 0，不该拦误报 0**。
- **分层完备测试（2026-08-04，规则粒度补测）**：场景矩阵之外，对 L0–L4 加出口通道、归一化预处理**每层每条规则**（正例／白名单豁免／边界）另建 78 条向量逐条验证，实例真跑三段全绿（含 Presidio 逐实体、Bedrock L4 标定段）；2026-08-05 按最新引擎重跑**零差异**（无回归）。
- **拦截延迟**：BLOCK 类请求 38–110 ms 内被网关 400 拒绝（内容不出网关）；网关内 DLP 同步扫描 p50 ≈ 28 ms、p95 ≈ 53 ms；短文本请求开 DLP 的净成本约 **45 ms/请求**。
- **吞吐边界（诚实标定）**：短文本 16 并发 qps ≈ 32（关 DLP 对照 ≈ 110）；**~2000 token 长文本高并发下单副本 Presidio 单核打满，p50 劣化至 7.6 s**——长文本生产流量须 Presidio 多副本扩容后复测，这是部署配置问题而非架构缺陷。
- **L4 语义告警（Bedrock 功能标定，非生产）**：无签名的语义敏感内容（经营策略／未公开财务／自研架构）同步链路按设计放行，异步告警秒级触发：**Qwen3-32B 类别判定 4/4 全对（含阴性对照不误报），Llama-3.1-8B 3/4**。同步裁决零污染。**此标定数据出 VPC，仅证功能可行；生产 L4 必须自托管（VPC 内 GPU + vLLM）。**
- **弱 NER 教训（实测发现并修复）**：Presidio 的 spaCy 人名／地名识别在中英混排下会把整句、hex 片段误标为 PII（恒 0.85 分）。已在引擎层加合法性过滤＋强实体佐证规则：人名／地名单独出现不再触发同步脱敏，交 L4 异步复核——这正是「分层裁决」设计的价值：统计型信号不配单独拿同步否决权。

**方案二实测已完成（详见《方案二-03-测试报告》《方案二-04-真机踩坑实录》）**：

- **验证节点四层测试全绿**（2026-07-30）：CA 三级链严格校验、选择性 bump（仅推理域名解密，认证域名原生透传）、三态 wire-byte 铁证（REDACT 后上游收到的明文 PII 消失、BLOCK 请求零字节出网）、fail 语义四子测（fail-closed 严格分流）。
- **真实 Kiro 桌面端端到端三态全绿**（2026-08-03）：PASS 正常回答／REDACT 手机号链路遮蔽（工具目录与协议字段逐字节完好）／BLOCK 真密钥拦截。**合成测试全绿 ≠ 真机可用**——接入真实客户端后连修六个「输入假设」级缺陷（工具目录高熵误报、会话历史重扫、协议字段 NER 误判、脱敏跨字段污染等），全程复盘见踩坑实录。
- **Tier D 逐层探针经真实代理链路**重验 L0–L3.5（2026-08-05，verdict + top_layer 双断言 8/8）。

尚待验证：
> - 两方案共同：**压测下的拦截成功率与拦截延迟**（现有压测只测了「干净流量的通过延迟」，高并发下 BLOCK/REDACT 是否仍 100% 正确拦截、拦截路径延迟分布如何，未系统测量）；
> - 长文本 Presidio 多副本扩容后复测；
> - default-deny 出口白名单对盲区外发的兜底拦截情况。

---

*本方案不承诺杜绝泄漏。它承诺的是：把可控的路径做干净，把有代价的路径标清楚，把兜不住的盲区诚实告诉你，并让整套体系可审计、可向监管交代。我们把钱和信任投在 opt-in 网关 + opt-out 合同 + `.kiroignore` + default-deny 出口 + 诚实标定上，而不是投在把全司明文集中到一台海外 EC2 的 MITM 上。诚实标定，才是最佳实践与营销话术的分水岭。*
