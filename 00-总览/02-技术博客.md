# 当研发开始用 AI 写代码：如何在不骗自己的前提下，管住流向大模型的数据

> 这是一篇讲「怎么做」也讲「做不到什么」的技术博客。企业 AI 数据防泄漏领域充斥着「一键合规」的营销话术，但真正决定成败的，是你有没有在拿明文的那个点上动手、有没有把兜不住的盲区诚实标出来。本文覆盖两套方案的设计与协议细节，两套方案均已在 AWS us-west-2 真实环境完成实测（方案一四阶段 + 分层完备，2026-07-30/08-04/05；方案二验证节点四层 + **真实 Kiro 桌面端端到端**，2026-07-30/08-03/05 + k6 压测 08-11），文中数字全部实测、不造。

---

## 一、背景与需求

### 1.1 三个正在发生的泄漏现场

AI 编码助手、Agent、MCP 工具链进入研发日常之后，数据外泄的形态变了。传统 DLP 盯的是文件外传、邮件附件、U 盘拷贝；而现在，泄漏发生在一条条到大模型域名的、加密的、看起来完全正常的 HTTPS 连接里。

- **现场一 · 手动粘贴。** 工程师把一段报错堆栈连同源码贴进 AI 助手求解，内部逻辑、内网地址、甚至密钥就此出境。
- **现场二 · 工具自动打包。** 用闭源 AI 编码工具（如 AWS Kiro）时，为了让补全更准，工具会把代码库上下文自动打包进推理请求——开发者并没有「主动发送」的动作，数据已经走了。
- **现场三 · Agent 自主外发。** Agent 执行 `git push`、`curl`、调用外部 API、或经扩展进程回传，密钥与业务数据流向任意可达目的地，且完全不经过可观测的推理接口。

这三个现场的共同点：流量默认全部出境到海外云端大模型；出口网关看到的只是「一个到某模型域名的加密连接」，看不到里面是什么。

### 1.2 三类真实需求（先分清，别混谈）

企业口中的「防止信息发给大模型」，其实是三个不同的诉求，缓解手段完全不同：

- **防训练／防留存**：不希望内容被用于模型训练或长期留存。**最高性价比的手段是合同，不是技术**——用企业版身份中心（IdC）签订 opt-out（不训练／不留存）条款即可覆盖大部分场景。
- **防误贴／防外发**：不希望机密在「发出前」就流出，希望有一道同步的内容审查。这才是需要 DLP 引擎的场景。
- **防出境**：数据不能离开境内。**这一条 Kiro 从根上满足不了**——它没有中国区（仅 us-east-1／eu-central-1），代码必然出境。DLP 只能降低出境内容的敏感度，不能消除跨境这件事本身。上任何技术方案前，先与需求方对齐到底要的是哪一类，否则会用错工具、给错承诺。

## 二、问题的本质

### 2.1 第一性原理：内容审查只能发生在「能拿到明文」的点

要审查内容，你必须先看到内容。TLS 之后的信道是加密的，任何工作在 TLS 之下的设备（比如只读 ClientHello 里明文 SNI 域名做白名单转发的 SNI 透传代理）永远看不到 prompt、源码、请求体——它是个「不拆信、只看信封收件地址的邮差」。

所以「我已经有一台 SNI 透传代理了，加个 DLP 模块就行」这条路走不通。要审查内容，只有两个可以拿到明文的点：

1. **客户端进程内**（数据加密之前）；
2. **一个终止 TLS 的代理**（把 TLS 在中途解开）。

这就把问题逼到了一个分叉上。

### 2.2 决定一切的分叉：客户端能不能改 `base_url`

- **能改 `base_url`**（自研 Agent／SDK／AI 应用）：让客户端**主动**把请求发到你的网关。网关是一个**opt-in 的、有名有姓的合法终点**——客户端明确知道自己在跟网关说话，网关也就自然拿到了明文。**不需要伪造证书，不需要分发企业 CA，不破坏任何 TLS 信任。** 这是干净的路径。
- **不能改 `base_url`**（闭源工具，推理端点硬编码）：客户端认定自己在直连某个固定域名。你想在中途看内容，只能**冒充**那个域名——伪造证书、让客户端信任你签发证书的企业 CA、半路把信拆开。这就是 **MITM（中间人）**，是有真实代价的路径。

一句话记住这两者的区别：**LiteLLM 网关是「你告诉客户端来找我」（opt-in 终止）；MITM 是「我假装我是它要找的那个」（拦截）。** 前者合法透明，后者你等于替全体开发者的加密信道背书。**能改 `base_url` 就别做中间人。**

### 2.3 内容型 DLP 的本质局限（这一节决定你会不会骗自己）

必须在设计之初就把这句话钉在墙上：**内容型 DLP 是 best-effort 的检知（detection），不是硬预防（prevention）。扫描通过 ≠ 无泄漏。**

原因是根本性的：**一段内容是否属于「本公司机密、不该出境」，往往无法仅凭内容本身判断**——它取决于业务归属和上下文，而不是文本特征。因此：

- 对**已登记的指纹**（密钥格式、内部术语表、EDM 精确数据匹配）——**强**，召回率高。
- 对**新写的源码、改写过的业务逻辑**——**系统性漏检**。一段刚写出来的核心算法，没有任何已知指纹能命中它。

### 2.4 数据驻留 ≠ 内容审查

再强调一次，因为最容易被管理层混淆：把审查代理部署在境内，不等于数据留在境内。Kiro 的推理终点在海外，**代码必然出境**。DLP 处理的是「出境的是什么」，处理不了「出不出境」。这两件事要分开向管理层交代。

## 三、方案一 · LiteLLM 统一网关（面向可配置 `base_url` 的自研应用）

### 3.1 定位

方案一治的是**能改 `base_url`** 的那一类客户端：你自己写的 Agent、SDK、AI 应用。它是一个 opt-in 的 TLS 终止网关——客户端主动把 LLM 请求指向它，它拿到明文，在转发给上游模型之前做内容审查。

客户端接入只是改一行 base_url（示意）：

```python
from openai import OpenAI

client = OpenAI(
    api_key="<litellm-virtual-key>",
    base_url="https://ai-gateway.corp.internal/v1",  # 指向企业自有 LiteLLM 网关
)
```

因为是客户端**自愿**把流量交过来，网关是合法明文终点，**无需伪造证书、无需企业 CA**。

### 3.2 两道审查钩子

- **prompt 审查（`pre_call_hook`）**：请求送往上游模型前，对 prompt 全文过 DLP 引擎，命中则脱敏改写或阻断。
- **MCP 工具调用审查（`pre_mcp_call` guardrail）**：LiteLLM 的 MCP gateway 能在工具被调用前审查其**参数**——防止敏感数据经工具调用参数外泄。这与 Symantec 公开的 LiteLLM guardrail 实践一致。

自定义 guardrail 的骨架（示意，非实测代码）：

```python
from litellm.integrations.custom_guardrail import CustomGuardrail

class CorpDLPGuardrail(CustomGuardrail):
    async def async_pre_call_hook(self, user_api_key_dict, cache, data, call_type):
        for msg in data.get("messages", []):
            verdict = dlp_engine.scan(msg.get("content", ""))   # 见 3.3 分层引擎
            if verdict.block:
                raise ValueError(f"DLP blocked: {verdict.reason}")
            msg["content"] = verdict.redacted_content            # 脱敏改写后放行
        return data
```

### 3.3 DLP 分层引擎（方案一、方案二共用）

按「便宜且准 → 贵且模糊」逐层递进，命中即止：

| 层 | 手段 | 抓什么 | 特点 |
|---|---|---|---|
| L0 | 正则 / 关键词表 | 固定格式密钥、内网域名、禁用词 | 最便宜、零延迟 |
| L1 | detect-secrets / gitleaks | 各类凭证、token | 成熟、误报可控 |
| L2 | 高熵检测 + 语境 | 未知格式的高熵串 | 抓 L0/L1 漏网的疑似密钥 |
| L3 | Presidio | PII（姓名、邮箱、身份证等） | 开源、可扩展识别器 |
| **L3.5** | **内部术语表 / EDM 精确匹配** | **公司专有名词、注册过的机密数据** | **性价比最高的一层** |
| L4 | 本地／VPC-only LLM | 需语义理解的敏感判断 | **绝不能用第三方 LLM——那是二次外发** |

> **红线：L4 的语义审查模型必须本地自建或部署在自有 VPC 内。** 用任何第三方托管 LLM 去「审查外发内容」，等于把要保护的内容又发出去一次，是第二条泄漏通道。
>
> ⚠ **演示例外（红线不变）**：为让读者/客户**打开即可端到端验证 L4 功能**，方案二 `:9000` 判定服务的 committed 默认把 L4 后端设为 **Bedrock（内容出 VPC）**、模式为 `async`（异步告警、绝不改 verdict）。这是**知情的演示/标定 shipped default**，已在 config/compose/启动日志/文档多处刺眼标注为**非生产**；生产部署**必须** `DLP_USE_BEDROCK_L4=false` 并切自托管 VPC-local（GPU+vLLM）。L4 在方案二是三态开关 `DLP_L4_MODE ∈ {off, async, sync}`：`sync` 为显式可选阻断态（高置信就地合成 BLOCK、`top_layer=L4`），且超时即降级为异步告警放行——引擎 `scan()` 自身仍恒不因 L4 改 verdict，`sync` 的 BLOCK 是在 **server 层（引擎之外）** 合成。

> **两方案共用同一引擎，但调用方式有意不同（这是设计，不是不一致）。** 方案一网关（LiteLLM callback）与引擎**同进程**，直接 `import dlp` **in-process 调用** `DLPEngine.scan()`；方案二的 mitmproxy addon 与引擎在**两台物理主机**上（addon 在 MITM 节点、引擎在 DLP 主机），addon 解密后把明文 body **POST 到 DLP 容器 `:9000/inspect`** 做裁决。为什么不统一成 `:9000`：
>
> 1. **物理主机隔离决定传输层**：方案二 addon 与引擎天然跨机，只能走 HTTP；方案一两者同机同进程，直调省掉一次序列化 + 一跳网络 RTT，延迟更低、故障面更小。
> 2. **方案一有 per-request 独有能力**：网关按注入点（prompt / MCP / flowback）传不同 `injection_point`、维护会话滑窗、对多模态请求分段扫描后写回——这些需要与请求生命周期同进程耦合，`:9000` 的无状态 body-in/verdict-out 接口表达不了。
> 3. **权衡显式化**：`:9000` 的价值是**跨语言/跨主机复用**（addon 是 Python、但引擎可换任意语言重写而 addon 不改）；方案一不需要这层解耦，强行加 HTTP 只会徒增延迟与运维面。
>
> 两条路径调用的是**同一份 `engine/dlp/` 源码**（方案二容器以 `:ro` bind-mount 挂载），行为一致；差异只在传输层与方案一的请求级增强。

### 3.4 适用边界

方案一干净、轻量（单 EC2 + Docker 可起）、风险低。但它**只对能改 `base_url` 的客户端有效**。对 Kiro 这类推理端点硬编码、无法重定向的闭源工具——**方案一直接无效**，因为 Kiro 根本不会把请求发到你的网关。这就引出方案二。

## 四、方案二 · Kiro 透明拦截（面向硬编码、无法重定向的闭源工具）

### 4.1 先说清楚：为什么网关方案对 Kiro 无效

Kiro 的推理请求**硬编码**发往 `runtime.us-east-1.kiro.dev`，**没有 `base_url` 覆盖入口**。你无法让它主动来找你的网关。因此想在内容出境前看一眼，唯一的技术手段是**透明 MITM**：在流量路径上终止 TLS、冒充那个硬编码域名。

> MCP gateway 对 Kiro 是**弱 DLP**：Kiro 的**原生工具**（读文件、执行 shell、代码库检索）**不走 MCP**，其数据被直接打包进 runtime 推理流出境；gateway 只看得到 remote MCP，看不到原生工具，也看不到 stdio MCP。所以指望「给 Kiro 配个 MCP 网关就能审查」是不成立的。

### 4.2 推理面协议细节（用于正确解析与改包）

- 推理端点：`runtime.us-east-1.kiro.dev`
- 操作：`GenerateAssistantResponse`（服务 `AmazonCodeWhispererStreamingService`）
- 编码：`x-amz-json-1.0`；操作名在 HTTP 头 `X-Amz-Target` 里
- 响应：event-stream 流式；MITM 侧只读转发，设 `flow.response.stream = True`

### 4.3 关键修正：推理面用 Bearer，不是 SigV4

这一点直接决定「能不能改包／阻断」：**Kiro 推理面用的是 Bearer token（OIDC/SSO），不是 SigV4。**

- SigV4 会对 body + host 做签名，任何改动都会导致签名失效——若推理面是 SigV4，DLP 就只能「原样只读转发」，改包/阻断做不了。
- 但推理面实测是 **Bearer**，签名不覆盖 body/host，因此**在推理腿上安全地改写 body、脱敏、阻断是可行的**。
- **注意**：任何可能存在的 SSO 腿 / Bedrock-direct 腿若走 SigV4，则那些腿必须**只读透传**，绝不改包。认证/SSO 域名（`oidc`、`portal.sso`、`*.awsapps.com`、`management.kiro.dev`、`cli.kiro.dev`）继续走 ssl_preread 透传，**永不 bump**。

### 4.4 选择性 bump：把「透传管道」局部升级为「中间人」

不要把整台代理都改成 MITM。用 nginx `stream` 的 SNI map **只对推理端点这一条** bump 到本地 mitmproxy，其余全部继续透传，未知目的地默认拒绝（示意配置）：

```nginx
stream {
    map $ssl_preread_server_name $upstream {
        runtime.us-east-1.kiro.dev   127.0.0.1:8443;   # 仅此一条 bump 到本地 DLP

        # 认证 / SSO 域名：继续 ssl_preread 透传，永不 bump
        oidc.us-east-1.kiro.dev      passthrough_kiro;
        management.kiro.dev          passthrough_kiro;
        cli.kiro.dev                 passthrough_kiro;
        # portal.sso.* / *.awsapps.com 同理

        default                      deny;             # 其余一律拒绝
    }

    server {
        listen 443;
        ssl_preread on;
        proxy_pass $upstream;
    }
}
```

本地 mitmproxy addon 终止 TLS、解析 CodeWhisperer 协议、调 DLP、决定阻断/放行（示意）：

```python
def request(flow):
    target = flow.request.headers.get("X-Amz-Target", "")
    if target.endswith("GenerateAssistantResponse"):
        body = parse_codewhisperer(flow.request.raw_content)   # x-amz-json-1.0
        verdict = dlp_engine.scan(extract_prompt_and_context(body))
        if verdict.block:
            flow.response = http.Response.make(403, b"DLP blocked")   # Bearer 面可安全阻断
        else:
            flow.request.raw_content = reserialize(redact(body))       # 脱敏改写后放行

def responseheaders(flow):
    flow.response.stream = True    # event-stream 响应只读转发，不缓冲整流
```

### 4.5 源头排除：`.kiroignore` + MDM

在到达推理之前就把敏感文件挡在上下文之外，是真正互补的一层：

- `~/.kiro/settings` 下的 `.kiroignore`、`kiroAgent.agentIgnoreFiles` 可通过 MDM 统一下发到全体端点。
- **未验证项**：codebase 索引 / embedding 是否严格遵守 `.kiroignore`、是否在本机之外计算——必须向 AWS 确认（见第七节必测④）。

### 4.6 MITM 兜不住的盲区（务必列清）

透明拦截只覆盖**已知的 HTTPS 推理端点**。以下路径它一概看不到：

- Agent 自主 shell 外发（`git push`、`curl`）；
- stdio MCP（本地进程间，不过网络代理）；
- Open VSX 扩展进程内独立回传；
- 原生工具数据被打包进推理流（虽走推理端点，但混在正常上下文里，DLP 未必能切出「这是不该发的」）。

**这些盲区只能靠 default-deny 出口白名单兜底**——默认拒绝所有出站，只放行白名单目的地。它不碰 TLS、不新建明文枢纽，却是唯一的结构性根控制，应**优先、先行**部署，而不是等 MITM 上了再补。

### 4.7 部署形态：C 本机 vs D 网关

上文 4.2–4.6 描述的是**网关式集中拦截（下文决策清单中记为 D）**：开发机的流量经既有网络路径（如 VPN/路由）到达同一台共享 EC2，由它统一执行选择性 bump、统一留痕、统一审计。这不是唯一的部署形态，还有一个更保守的变体：

- **C · 客户端本机 MITM**：把同一套「选择性拦截」逻辑（本地 mitmproxy + 4.2–4.4 的协议解析/DLP 调用逻辑）搬到**每台开发机自己身上**，绑定在 `127.0.0.1`。流量导向不必依赖网络路径改造——Kiro 官方支持 `HTTPS_PROXY`/`HTTP_PROXY` 环境变量与 Settings → Proxy 配置，可以直接把该机的 Kiro 流量指向本机代理（是否所有 3–4 条 TLS 栈都遵守这个代理设置，同样需要按栈实测，逻辑与第七节的 CA 分发一致）。企业 CA 只需装在这一台机器上——仍要面对同一套 3–4 栈信任问题，只是范围缩小到单机。

两种形态的取舍：

| | C 本机 | D 网关 |
|---|---|---|
| 爆炸半径 | 小——单台机器的 CA/私钥泄漏只影响这一台 | 大——一套 CA、一个节点是全公司推理流量的单一明文枢纽 |
| 集中强制力 | 弱——依赖代理进程持续运行、CA 正确安装，中心侧难以确认是否被关闭或绕过 | 强——不依赖开发机配合，统一留痕、统一审计 |
| 适用前提 | 端侧可信（受管理设备，有 EDR/MDM 可验证代理确实在跑） | 端侧不可信，或需要统一强制策略 |
| 是否仍需正式评审、不可静默上线 | 是——范围变小不等于风险性质变了 | 是 |

两者都不改变第 2.2 节的核心权衡：**只要终止 TLS、注入 CA，就是在为某个信任边界内的加密信道背书**——C 缩小的是「背书的范围」，不是「要不要背书」这件事本身。

## 五、诚实标定（给管理层的话）

- **分层，不是银弹**：任何单点都不完整，正确姿势是纵深防御。
- **内容型 DLP 是 best-effort 检知**：对已登记指纹强，对新源码/改写逻辑系统性漏检；**扫描通过 ≠ 无泄漏**。
- **数据驻留 ≠ 内容审查**：Kiro 无中国区，代码必然出境，DLP 只降低不消除跨境。
- **MITM 有真实代价**：终止 TLS + 注入企业 CA = 你为全体开发者的加密信道背书，形成全司明文单点、扩大 CA 攻击面、可能被定性为监听。只作补充层，绝不静默上线。
- **最隐蔽的风险是虚假安全感**：「0 命中」的绿灯可能由多重盲区叠加而成，误导管理层扩大使用面，反而抬高暴露。**上了检测栈，也不能撤掉人工管控。**

## 六、分层落地路线图

### 决策清单：从「你的威胁模型」直接选路径

先把前面出现过的控制手段贴上字母标签，方便复用：

- **A · 合同与事后可审计**：IdC 企业版合同性 opt-out（不训练/不留存）+ prompt logging 落自有 S3 + Macie/EventBridge 事后（近实时）告警。不碰 TLS、不看内容，只解决「模型商会不会拿这批数据训练/留存」和「出了事能不能查」两件事。
- **B · 出口与扩展白名单**：现有 SNI 代理收紧为 **default-deny 出口白名单**（默认拒绝所有出站，只放行已知目的地）+ 把可安装的 IDE 扩展来源限制为内部策划的白名单（而非任意 Open VSX 扩展，即「扩展 registry」）。不解密任何内容，只管「流量能去哪、能装什么」——这是 agent 自主 shell 外发、MCP 连任意 API、恶意/失控扩展回传（4.6 的三大盲区）**唯一**能兜住的控制。
- **C · 客户端本机 MITM**（见 4.7）：选择性拦截逻辑跑在开发机本地，CA 只装这一台机器，爆炸半径最小，但依赖端侧可信、集中强制力弱。
- **D · 网关式选择性 MITM**（即上文方案二，4.1–4.6）：选择性拦截逻辑跑在共享 EC2 网关，统一强制、统一留痕，但爆炸半径是全公司级的明文单点。

有了 A/B/C/D，威胁模型可以直接映射到路径，不必先读完全文再自己拼：

| 你的真实威胁模型 | 推荐路径 | 需要 MITM？ |
|---|---|---|
| 只担心内容被用于训练 | A 的 opt-out 部分 | 否 |
| 担心内容留在 AWS 侧、要可审计 | A（opt-out + prompt logging + Macie/CloudTrail） | 否 |
| 担心开发者误贴机密，接受事后近实时告警 | A + B | 否 |
| 担心 agent shell / MCP / 扩展乱外发 | B 的 default-deny 出口 + 扩展 registry（MITM 对此无效） | 否 |
| 内容离开边界前必须同步硬阻断 + 端侧可信 | A + B 打底，再加 **C** + 分层 DLP | 是（本机） |
| 同上但需集中强制、端侧不可信 | A + B 打底，再加 **D** + 分层 DLP | 是（网关） |
| 硬约束是「代码不能出境」 | 不用 Kiro / 换国产替代 | 不适用 |

**读表的方式**：从上往下越靠上越轻、越不碰 TLS。只有当真实需求落在表格下方两行——「同步硬阻断」是不可退让的硬性要求——才需要认真考虑 MITM，且要先判断端侧可信度以选 C 还是 D。**多数公司的多数威胁模型停在 A + B 就已经解决，走不到 MITM 这一步。**

### 落地顺序

- **第 0 层（立即做，不碰 TLS，覆盖最广）**：
  - 自研可配客户端 → LiteLLM 网关（方案一）；
  - Kiro → **A**（IdC 企业版合同性 opt-out + prompt logging + Macie/EventBridge 告警）+ MDM 下发 `.kiroignore` + **B**（现有 SNI 代理收紧为 default-deny 出口白名单 + 扩展 registry 白名单）。
  - **多数威胁模型到此为止。**
- **第 1 层（仅当「出境前必须同步硬阻断」是硬性监管要求）**：在第 0 层之上，受控引入 **C 或 D**（按端侧可信度二选一，见上表），全部硬门槛（第七节）到位。**失败模式建议降级为透传 + 告警**；若业务坚持硬预防，则回到 fail-closed（拦截失败即阻断），并书面接受可用性代价。
- **治理贯穿**：书面标定检测栈覆盖边界；仪表盘明确标注「非泄漏保证」。

## 七、上 MITM 前的必测项 + CA 硬门槛

### 必测项（缺一不可，勿当已知）

1. **证书固定**：自建 CA 实跑，确认 Kiro 不做证书固定（cert pinning）；且客户端每次自动更新后**复核**。现有间接证据强烈指向「无固定」——业界已有**零客户端改动**即可拦截 `kiro-cli` 的 MITM 实践，且现场失败均为「签发者不受信任 / 自签名证书在链中」（`UnknownIssuer` / `SELF_SIGNED_CERT_IN_CHAIN`）类错误、信任 CA 后即恢复（与证书固定的表现正相反）；但证据横跨多个版本，仍须对**目标推理 host + 目标客户端版本**实跑复核。
2. **数据面认证模型**：抓包确认推理面确为 Bearer（据此才能改包/阻断），并识别是否存在 SigV4 腿（那些腿只读透传）。
3. **真实推理 host 与 ALPN**：抓包确认 host 为 `runtime.*.kiro.dev`、协议为 event-stream（据此正确解析、设 `stream=True`）。
4. **索引合规**：向 AWS 确认 codebase 索引/embedding 是否遵守 `.kiroignore`、是否离机计算。
5. **各栈 CA 信任在目标 build 实际生效**：Kiro 不是单一 TLS 栈，而是 3–4 条各自独立信任证书的栈（见下「CA 硬门槛」的信任栈矩阵）。必须在**目标客户端版本**上逐栈实测「装了企业 CA 后握手是否真的通过」——尤其注意 Windows 上负责把系统证书库导入 Node 的 `win-ca` 模块曾因缺依赖静默崩溃，一旦崩溃会让 **OS 信任库与 `NODE_EXTRA_CA_CERTS` 同时失效**、Extension Host 全部 HTTPS 报 `SELF_SIGNED_CERT_IN_CHAIN`。**不能假设「装了就信」。**
6. **HTTP 层干扰 / 流稳定性**：即使 CA 已被信任、TLS 握手成功，仍需实测代理是否在 HTTP 层破坏可用性——已知现场包括代理改写响应头把连接降级到 HTTP/1.0、以及大响应体下 event-stream 被中途 reset。这是与证书信任**相互独立**的失败模式，MITM 上线前必须单独验证。

### CA 硬门槛（做不到就不要上 MITM）

- **CA 信任不是「一个开关」，Kiro 有 3–4 条各自独立信任证书的 TLS 栈**——把企业 CA「装进系统」远不足以让所有栈接受它。每条栈信任 CA 的机制、需要的配置都不一样，必须按栈分别下发、逐栈实测：

  | TLS 栈 | 谁在用它 | 信任 CA 的机制 | 让它信任企业 CA 的手段 |
  |---|---|---|---|
  | Chromium / renderer | 界面、扩展市场、浏览器登录 | 自带 Chrome Root Store 作公开信任来源，但仍尊重管理员装进 OS 库的企业根 | 与推理**无关**——推理不走这条栈；仅影响界面/登录，而登录本就绕到 OS 网络栈 |
  | **Node / Electron 扩展宿主** | **IDE 的模型推理请求在这里发** | 内置 Mozilla 根 + 经 `@vscode/proxy-agent` 桥接的 OS 库（`http.systemCertificates` 默认开）+ `NODE_EXTRA_CA_CERTS` | **装进 OS 信任库**（首选，见下）**或** `NODE_EXTRA_CA_CERTS` 指向 CA 文件 |
  | Rust CLI | `kiro-cli` 本体 | rustls/reqwest，**不读 Windows 证书库、不认 `NODE_EXTRA_CA_CERTS`** | 必须 `SSL_CERT_FILE` / `AWS_CA_BUNDLE`（OIDC 登录腿仍可能单独失败，须实测） |
  | Bun TUI | CLI 的推理子进程 | BoringSSL，**忽略 `NODE_EXTRA_CA_CERTS`** | `NODE_USE_SYSTEM_CA=1` + 较新 CLI 版本（旧版代理链路不完整） |

- **因此「CA 覆盖」是多条并行、无单一保证的路径，不是设一个环境变量就万事大吉**：
  - `NODE_EXTRA_CA_CERTS` 的机制本身是**确定性**的（启动时读一次、追加到内置根而非替换），但它**只对走标准 Node TLS 的栈生效**，对 Rust/Bun 栈无效；且若 Kiro 自身代码显式传了 `ca`（explicit ca 会**替换**默认根、而非追加）、或走了自带证书库的 undici，它会被绕过——这些是真正的不确定来源，**不能假设它一定生效，必须在目标 build 上实测**。
  - **IDE 首选把企业 CA 装进操作系统信任库**，而非只设 `NODE_EXTRA_CA_CERTS`：GUI 应用从 Dock/开始菜单启动时**不继承 shell 环境变量**，环境变量法对 IDE 常常「设了没用」；OS 信任库经 `http.systemCertificates`（默认开）桥接进 Node 更耐用。**但仍受制于上面「必测项 5」的 `win-ca` 崩溃问题**——桥接一旦失效，OS 库这条路也会断。
  - **CLI 与 IDE 要分开配**：CLI 那条 Rust/Bun 栈既不吃 OS 信任库、也不吃 `NODE_EXTRA_CA_CERTS`，只认 `SSL_CERT_FILE`/`AWS_CA_BUNDLE`（Rust）与 `NODE_USE_SYSTEM_CA`（Bun）。**一套 CA 分发脚本盖不住所有栈。**
- **绝对禁止 `NODE_TLS_REJECT_UNAUTHORIZED=0`**——它关闭**全部**证书校验，等于自废 TLS，制造比原问题更大的漏洞；它也**不是**握手失败时的「临时绕过」（已知现场里握手报错的真正根因是上面的 `win-ca` 崩溃，设这个变量只会掩盖问题、同时敞开信道）。
- **X.509 Name Constraints**：mark critical、permitted 限定 `*.kiro.dev`、覆盖 iPAddress；且加在**会被强制校验的中间/叶层**（RFC 5280 允许客户端不处理 trust anchor 上的约束）；并**实测确认 Kiro 的 TLS 栈确实强制执行**这些约束。
- **私钥保护**：根 key 入 HSM/离线；理想形态是**节点不持签名 key**，仅对单一 host 通过 `KMS::Sign` 现签短期叶子证书——可审计、可秒撤（示意）：

```bash
# 节点不持私钥，按需向 KMS 申请对单一 host 的短期叶子证书签名
aws kms sign \
  --key-id "$LEAF_SIGNING_KEY" \
  --message fileb://leaf-tbs.der \
  --message-type RAW \
  --signing-algorithm ECDSA_SHA_256
```

> **先例警示**：Lenovo「Superfish/Komodia」预装无约束根 CA（catch-all），被 FTC + 多州联合处罚、达成约 350 万美元和解；US-CERT TA17-075A《HTTPS Interception Weakens TLS》、Concordia《The Sorry State of TLS》都记录了拦截设备普遍不校验上游证书导致的系统性降级。**无 Name Constraints 的企业根 CA = 一把万能钥匙的皇冠明珠，一旦泄漏后果远大于它想防的泄漏。**

## 八、合规风险（技术方案上线前必须走完）

- **勿静默上线**：MITM 在协议层与真实中间人攻击**不可区分**。未告知的部署 = 未授权监听。必须经正式安全评审、告知使用者并取得同意。
- **EU/德国雇员**：涉及员工监控须经 works council 共同决定（BetrVG §87(1) Nr.6），签订 Betriebsvereinbarung 后方可推行。
- **跨境出境**：境内→美国的数据出境需走中国的数据出境安全评估/标准合同；同时评估美国 CLOUD Act 暴露。**先由法务定性，再谈技术。**

## 九、总结

- **三条底线**：① 拿明文才能审内容——能改 `base_url` 走网关（干净），不能改才谈 MITM（有代价）；② 内容型 DLP 是 best-effort 检知，不是硬预防，扫描通过 ≠ 无泄漏；③ MITM 的盲区只有 default-deny 出口白名单兜得住，它才是根控制。
- **把钱和信任投在**：opt-out 合同 + `.kiroignore` + default-deny 出口 + 诚实标定，而不是投在把全司明文集中到一台海外 EC2 的 MITM 上。
- **实测结果（两套方案均已完成实测）**：

> **方案一** 已在 us-west-2 真实单机（m7i.2xlarge：LiteLLM + 分层 DLP 引擎 + Presidio en/zh 双语 NER + Bedrock L4 标定）跑完四阶段，全部数字实测（完整矩阵见《03-方案一测试方案》§8）：
> - **功能**：离线 56/56，网关端到端 46/46；漏拦 0、误报 0 两条硬门达标。flowback 回流 hook、session 滑窗拼接（拆分密钥两条消息重组后 BLOCK）、MCP 入参扫描均实测生效。
> - **延迟**：DLP 同步扫描 p50≈28ms / p95≈53ms（L3 Presidio HTTP 占绝对主体，L0–L2/L3.5 合计 <1ms）；BLOCK 在 38–110ms 内 400 拒绝；短文本开 DLP 净成本 ≈45ms。
> - **吞吐（诚实标定）**：短文本 c16 qps≈32（对照关 DLP ≈110）；**~2000 token 长文本把单副本 Presidio 单核打满，c8+ p50 劣化到 7.4s、qps 1.1**——docker stats 归因清楚（presidio 84–107%，litellm <8%）。长文本生产必须 Presidio 多 worker 扩容，属部署配置而非架构缺陷。
> - **L4 语义（Bedrock 标定，数据出 VPC，非生产）**：套件 6 同步全放行（架构性缺口按设计成立），异步告警秒级触发带追溯上下文；类别判定 Qwen3-32B **4/4**（含阴性对照不误告警）、Llama-3.1-8B 3/4（漏自研架构类）。同步 verdict 零污染。生产 L4 仍须 VPC 内自托管。
> - **一条反直觉教训**：Presidio 的统计型 NER（人名/地名）在中英混排下误报严重到不可直接用于同步裁决（整句中文被 en 模型标成 PERSON、hex 片段被 zh 模型标成人名，且恒 0.85 分无从卡阈值）。修复是把弱 NER 降级为「需强实体佐证才参与同步，否则交 L4 异步」——分层引擎里，**每一层拿到的否决权必须与它的信号置信度匹配**。
>
> **方案二**（验证节点四层 2026-07-30 + 真实 Kiro 桌面端端到端 2026-08-03 + Tier D 逐层探针 2026-08-05 + k6 压测 2026-08-11，完整证据见《方案二-03-测试报告》《方案二-04-真机踩坑实录》）：
> - **bump / 透传红线**：curl/openssl 严格 TLSv1.3 校验，bump 域下发我方伪造链（`leaf→inter→root`，Verify=0），透传域 issuer 恒为原生 `Amazon RSA 2048`——只解密推理腿、其余从不解密。
> - **真机端到端可用性（含证书固定这一悬念）**：真实 Kiro 桌面端经 macOS hosts override → 选择性 bump → VPC 内 DLP → 真实上游，**三态（PASS 正常回答 / REDACT 手机号遮蔽 / BLOCK 真密钥拦截）全部按预期工作**。这本身回答了「证书固定」——**被测 Kiro 构建未做硬 pinning**，接受了我方 CA，MITM 可行（正式 pinning 三分判据仍留在《03》§6，换构建须重判）；握手成功、推理流转发贯通即端到端可用性的直接证据。**但「合成全绿 ≠ 真机可用」**：接真实客户端后连翻三轮，修了六个「输入是协议不是文本」级的坑（工具目录 L2 高熵误报、会话历史重扫、协议字段 NER 误判、脱敏跨字段污染等，见《04》）。
> - **压测（k6，2026-08-11）**：`/inspect` 净裁决合法吞吐拐点 ≈200–250 req/s，负载下拦截率 100%、误杀率 0、明文泄漏=0；Presidio 死端口下本地层仍 100% BLOCK、L3 类全部 `forced_block` 转 fail-closed、泄漏仍 0（《03》§8）。
> - **诚实边界（仍未系统覆盖）**：`.kiroignore` 索引合规、Bearer 认证面的完整枚举未做专项测；`/inspect` 压测是引擎裁决净成本，不含 MITM 真链路 TLS/转发时延（那部分是 Tier D 定性证据、非分位）；default-deny 出口白名单是网络层兜底控制，不在本轮 DLP 测试作用域内。
