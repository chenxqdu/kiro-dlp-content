核心教训一句话:**内容检测引擎的单元测试对象是"文本",但生产输入是"协议"。**
真实 AI IDE 的请求体里,用户输入只占极小一部分,其余全是客户端注入的工具目录、
会话历史、协议元数据——它们每一类都会以不同方式骗过为"扫文本"设计的检测层。

## 1. 前史:被误诊三轮的 "Too many requests"

**症状**:真实 Kiro 发任何消息报 `Too many requests, please wait before trying again.`

**误诊过程(诚实记录)**:最初把它当成 DLP 服务性能问题——真实 Kiro body ≈ 317KB
(每次推理都带系统提示 + 工具 schema + 全量历史),presidio 单 worker 串行扫完要
~24s,远超 addon 的 `DLP_TIMEOUT=8s`,于是 addon fail-closed 回 503,Kiro 重试
风暴表现为 429 文案。围绕这个诊断修了两层:

- **presidio 容器 `WORKERS=1→8`**:并发扫描,24.3s → 5.5s;
- **引擎 `l3_budget_s=6.0` 硬时间预算**:并发扫描累计超预算后,未完成变体一律标
  `incomplete` → 上层 fail-closed 升 BLOCK,绝不静默当 PASS(用 700KB 病理 body
  验证了截断路径)。

这两个修复**真实且必要**(没有它们,后面的坑根本没机会暴露),但**不是**报错的主因:
修完后真机报错依旧,只是形态从"卡死重试"变成了干脆的 `CorpDLPBlockedException`——
这才暴露出真正的主线:**不是扫得慢,是扫出了不存在的密钥**。

> 教训:症状(429)→ 归因(超时)的链条里每一环都要真机数据钉死。当时只有合成
> 数据,第一个"讲得通"的假设就被当成了结论,代价是三轮返工。

## 2. 坑1:L2 高熵检测把"工具目录"判成密钥(第一轮 BLOCK 主因)

**症状**:任何问题(包括"帮我写个快速排序")都返回 `CorpDLPBlockedException`。

**数据证据**:mitm 节点决策日志,单条请求 75 个 BLOCK 级命中,**全部**落在
`…userInputMessageContext.tools[N].toolSpecification.description`,规则清一色
`L2 high_entropy_secret`。离线复现:同一 body 去掉 `tools[]` 后 0 命中。

**根因是一个三因素连环**:

1. **客户端注入**:Kiro 每次请求自动携带 100+ 条 MCP 工具定义(name/description/
   inputSchema),这不是用户输入,是客户端 boilerplate;
2. **变体折叠制造假高熵**:引擎的 `stripped-sep` 预处理变体会删除所有分隔符——
   一段普通英文工具描述(如 *"Send an authenticated request using the bearer
   token…"*)被折叠成 ≥20 字符的连续串,香农熵轻松越过 4.0 阈值;
3. **语境词无词边界**:L2 的语境正则 `_CTX` 写的是 `credential|auth|bearer` 等
   **裸子串**——`auth` 匹配 author**iz**ation/authenticated,`credential` 匹配
   credentials。工具描述里这些词俯拾皆是,±40 字符语境窗口必然命中。

三者相乘:每条工具描述 = 高熵 token + 语境词 → `GENERIC_SECRET` BLOCK。
**用户写什么根本不重要,请求必死。**

**修法(F1 + F2 + F3,三层同时下手)**:

- **F1 抽取跳过**([`engine/dlp/extract.py`](../engine/dlp/extract.py)):
  `_SKIP_SUBTREE_KEYS = {"toolSpecification"}`,`_walk` 遇到该键整棵子树不产出
  扫描单元。只跳工具**定义**;工具**调用参数/结果**不在此键下,仍全量扫,不留
  数据外泄口。
- **F2 L2 变体门控**([`engine/dlp/engine.py`](../engine/dlp/engine.py)):L2 只扫
  **含义保真**变体(`raw` / `normalized` / `decoded:*`),不再扫 `stripped-sep` /
  `folded` / `session-window` 这类**结构重组**变体——"删空格把散文折成假高熵串"
  的机制从源头拆除。`decoded` 必须保留:还原 base64/hex/rot13 藏匿凭证正是熵
  检测的正当猎物(回归探针:base64 包裹的 AWS SK 仍 BLOCK ✅)。
- **F3 语境词加词边界**([`engine/dlp/l2_entropy.py`](../engine/dlp/l2_entropy.py)):
  `_CTX` 全词匹配 `\b(...)\b`,同时显式收录 `authorization` / `credentials`
  这两个真语境词;`authenticated` / `authorize` 等动词形态不再触发。

**关键澄清(部署时的实际疑问)**:抽取跳过**只改变引擎内部"扫哪些文本来计算
verdict"**,完全不改转发给上游的请求。DLP 是旁路检查器:PASS 时 addon 对
`flow.request` 一字不动原样转发(工具目录完整到达 Kiro);REDACT 时只把命中片段
替换、整棵 JSON 结构与未扫描子树原样保留。HTTP 层实测:REDACT 返回的
`redacted_body` 解析后 `tools=100/100` 完整。

**附带红利**:跳过工具目录 + 历史后,进入扫描的有效文本从 317KB 级降到 KB 级,
L3 延迟从 ~24s(修 F0 后 5.5s)进一步降到 **~20ms**,离 6s 预算线两个数量级。

## 3. 坑2:会话历史每轮重扫——冗余、误报放大器、REDACT 噪声源(第一轮 BLOCK 次因)

**症状/证据**:同一条 BLOCK 日志里,除工具目录外还有 34 个命中落在
`conversationState.history[…]`:历史里的英文注入上下文触发与坑1 同款的 L2 误报;
历史里 presidio 命中的人名/地名(John Smith / Seattle / 张伟)则把一切请求拖成
REDACT——**DLP 每轮改写一遍历史再转发**,既无谓又危险。

**根因**:CodeWhisperer 协议每次请求重发**全量**会话历史。而每条消息在它作为
`currentMessage` 首次发送的那一轮**已经被全量扫描并裁决过**——BLOCK 级内容根本
进不了历史(当轮就被合成 400 短路了)。每轮重扫历史:

- 检出上是**纯冗余**(fail-closed 语义下不存在漏网:漏检只可能发生在"当轮也漏"
  的场景,重扫历史救不回来);
- 性能上是**主要开销**(历史随会话线性增长,越聊越慢,最终顶到时间预算 fail-closed);
- 误报上是**放大器**(历史越长,假阳性面越大,且历史里的 PII 命中会反复触发改写)。

**修法(F2 之姊妹,进 [`extract.py`](../engine/dlp/extract.py))**:`_walk` 遇到路径
`conversationState.history` 整棵跳过——**增量扫描语义**:只扫本轮新增内容
(`currentMessage`),历史信任"当轮已裁决"。

**诚实标注的边界**:若密钥是在**本系统部署之前**的历史轮次贴入的,增量语义下不会
被追溯拦截(离线探针如实复现:密钥在 history → PASS)。这是增量扫描的定义性
取舍,不是缺陷;若要追溯,应一次性离线扫存量会话,而不是每轮在线重扫。

## 4. 坑3:协议字段被 NER 误判——`agentMode:"vibe"` 是个"地名"(第二轮 400 主因)

**症状**:修完坑1/坑2 后重测,Kiro 报 `Improperly formed request.`(AWS 400)——
错误形态**变了**:请求已通过 DLP 并转发到真实上游,是**上游**拒绝了 body。

**数据证据**:决策日志两条 REDACT,唯一命中:
`L3 presidio:location conf=0.85 fp=agentMode`。
presidio 把协议字段 `agentMode: "vibe"` 当英文单词识别成了 **LOCATION**,
REDACT 把它改写成 `[REDACTED:LOCATION]`,Kiro 服务端收到非法枚举值 → 400。

同轮日志还抓到同类未遂犯:`profileArn`(整串 ARN 判 PERSON)、`agentTaskType`
(枚举值判 LOCATION)、`additionalModelRequestFields.reasoning.effort`(`"high"`
判 PERSON)。任何一个被改写都是同款 400。

**根因**:NER 模型是为自然语言训练的,面对协议枚举值/ID/ARN 这类短字符串会
高置信度胡说;而抽取层此前把 JSON 里**一切字符串叶子**都送去扫描——协议字段
和用户内容在它眼里没有区别。

**修法(F4,进 [`extract.py`](../engine/dlp/extract.py))**:协议元数据字段全部
进跳过集——`profileArn` / `agentTaskType` / `additionalModelRequestFields` /
`agentMode` / `conversationId` / `chatTriggerType` / `customizationArn` /
`origin`(以及第三轮补的 `agentContinuationId`)。这些字段**永远不是用户内容**,
却全是 NER 误判高危;更要命的是它们一旦被 REDACT 改写就直接打坏请求合法性。

## 5. 坑4:脱敏作用域 > 扫描作用域——全局字符串替换的跨字段污染(第二轮 400 的深层 bug)

坑3 暴露的其实是一个**比误报更深的真 bug**:就算某字段"不扫",它也可能被改写。

**机制**:引擎的 `_redact_obj` 做的是**整棵 JSON 递归 + 全局字符串替换**——把
所有 REDACT 命中的 `matched` 文本在**每一个**字符串叶子里替换成掩码。于是:
只要 presidio 在**任何**被扫字段里命中了文本 `"vibe"`(比如用户 content 里真有
这个词),替换表就含 `("vibe" → "[REDACTED:LOCATION]")`,而 `agentMode:"vibe"`
**即使已经不被扫描**,也会在替换阶段被"顺带"污染。跳过集治了误报,治不了这个。

**修法(F5,进 [`engine.py`](../engine/dlp/engine.py))**:**脱敏作用域与扫描作用域
对齐**——`_redact_obj` 带路径递归,凡是抽取阶段跳过的子树(工具定义 / 协议字段 /
历史),脱敏阶段一律原样保留、不进入替换。单元探针钉死:替换表里塞入
`("vibe"→…)` 时,`agentMode` 纹丝不动,而用户 content 里的同一文本照常脱敏。

> 通用教训:**任何"改写请求再转发"的系统,改写范围必须 ⊆ 检查范围。**
> 两个作用域各自演化而不锁死等式,迟早出现"没检查的地方被改了"。

## 9. 已知残留(诚实清单,均为有意取舍)

1. **工具定义内藏密钥不检**:密钥若被塞进 `toolSpecification.description`(反向
   探针实测 PASS)。现实中该子树是客户端固定注入的 schema;若威胁模型包含恶意
   MCP 工具注册,应在工具**注册**环节检,而非每次推理请求重扫。
2. **历史不追溯**:部署前贴入历史的密钥不会被回头拦(见 §3 边界说明)。
3. **L2 弃扫结构重组变体**:用空格切开的泛型高熵密钥(无 `AKIA` 类前缀特征、无
   紧邻语境词)可能漏过 L2;有前缀特征的仍被 L0/L1 兜住。这是"散文误报机制根除"
   的代价,方向正确。
4. **presidio 中文 NER 噪声**:普通中文词(如"润色")偶被判 LOCATION/PERSON,
   导致 ① 类请求有时判 REDACT 而非 PASS——用户无感(改写的是 content 里不存在
   的匹配或无害片段),但属于多余改写,后续应做中文实体白名单/置信度调优。
5. **时间预算线**:超大上下文(粘贴整个大文件)仍可能顶到 6s 预算 → fail-closed
   BLOCK。这是安全侧优先的既定语义;跳过工具/历史后正常会话已远离该线。

## 10. 工程教训(可迁移)

1. **合成测试证明"机制对",只有真机流量证明"输入假设对"。**四层合成测试全绿的
   系统,接真实客户端翻车三轮——翻的全是"输入长什么样"的假设,没有一个是机制 bug
   的回归。
2. **先拿到真实 body 再归因。**"Too many requests" 被误诊为性能问题三轮,根因是
   诊断时手里只有合成 body。一条真机决策日志(75 命中全在 tools[])比三轮推理值钱。
3. **内容检测系统必须显式区分"用户内容"与"协议结构"。**工具目录、历史、协议
   字段各自以不同方式(假高熵/PII 噪声/NER 胡说)骗过为文本设计的检测层。
4. **改写范围 ⊆ 检查范围,用代码锁死而不是靠约定。**(坑4)
5. **NER/熵这类统计检测器,默认要词边界、要含义保真输入。**裸子串语境词与结构
   重组变体的组合是机制性误报,不是可以逐例修的个案。
6. **决策日志要"每决策一行紧凑摘要"。**本次定位全靠 `KIRO-BLOCK top=… rules=…`
   决策行;但 rules 全量 dump 在真机(数百命中)下刷爆 journal——摘要行 + 按需
   dump 才是对的形态。另注意 PASS 每 100 次才打一行,"没日志"≠"没经过"。
