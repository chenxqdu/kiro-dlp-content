# 方案二 · 设计与架构 —— 选择性 bump MITM + VPC 内 DLP 联动

> 本文是方案二的纲领文档，说明**为什么这样设计、每个组件做什么、哪些是绝不能碰的红线**。
> 部署步骤见 [`方案二-02-部署指南.md`](方案二-02-部署指南.md)，实测结论见 [`方案二-03-测试报告.md`](方案二-03-测试报告.md)，
> 逐条测试规程见 [`TEST-PLAN.md`](TEST-PLAN.md)。目录导航见 [`README.md`](README.md)。

---

## 0. 一句话定位

方案二 = **把一台 SNI 透传代理升级为「选择性中间人」**：在 nginx `stream` 层用 `ssl_preread` 读明文
SNI 做四层路由，**仅** `runtime.us-east-1.kiro.dev`（Kiro 推理腿）一条被引流到本机 mitmproxy 解密，
解密后的明文 body 交给**同 VPC 内的 DLP 判定服务**裁决，按 `PASS / REDACT / BLOCK` 三态处置；
**其余所有 SNI 一律 L4 透传、永不解密**。

它和方案一的根本区别：方案一是 **opt-in 网关**（客户端主动改 `base_url` 才被审，Kiro 硬编码
provider 用不了）；方案二是 **透明 MITM**（客户端只需信任企业 CA，无需改配置，能覆盖 Kiro）。
两者的 DLP 引擎是**同一套**（复用 `kiro-dlp-engine` 镜像），只是拦截点不同。

## 1. 为什么必须是「选择性」bump —— 三条设计约束

### 1.1 约束 A：认证模型决定了「哪条腿可以改包」

Kiro 有多条网络腿，认证模型不同，能否安全改写 body 也不同：

| 腿 | 域名 | 认证 | 能否解密改写 | 方案二处置 |
|---|---|---|---|---|
| **推理腿** | `runtime.us-east-1.kiro.dev`（`GenerateAssistantResponse`，AWS event-stream） | **Bearer / OIDC**（非 SigV4） | ✅ body/host 可安全改写、可短路 | **bump（解密审查）** |
| SigV4 腿 | `codewhisperer.*` / `q.*.amazonaws.com` | SigV4 签名 | ❌ 改一个字节签名就失效 | L4 透传 |
| 认证/SSO 腿 | `cli.kiro.dev` / `management.kiro.dev` / `*.awsapps.com` | OIDC 登录 | ❌ 最脆，一动就断登录 | L4 透传 |

**关键结论**：只有推理腿是 Bearer 认证，改 body/短路不会破坏签名——这正是「选择性」只 bump 它的
物理基础。SigV4 腿哪怕想审也不能改（改包 = 签名失效），所以对它们**只透传**。

### 1.2 约束 B：解密范围 = 攻击面 = 责任面，越小越好

TLS 中间人本质是「把全司明文集中到一台机器」，这台机器就是皇冠明珠靶心。解密的域名越多：
- 明文暴露面越大；
- 一旦证书私钥泄漏，可被伪造的域名越多；
- 合规审查/员工告知义务越重。

因此设计上把「必须解密才能审查的那一条」和「其余全部」严格分开——**bump 集合只有 1 个域名**。

### 1.3 约束 C：MITM 兜不住 agent 自主外发，需要 default-deny 兜底

MITM 只能看见「走已知 HTTPS 推理端点」的流量。它**看不见**：
- agent 自主 `shell`（`git push` / `curl`）；
- stdio MCP（走本地管道，MITM 完全失明）；
- Open VSX 扩展进程独立回传。

这些盲区只能靠 **SNI 代理的 default-deny 出口白名单** 兜底（nginx map 的 `default ""` = deny）。
方案二不声称「能拦住一切外发」——它诚实地只覆盖推理腿，其余靠白名单收口。

## 2. 拓扑（已验证工作）

```
┌──────────────┐        TLS (SNI 明文可见)        ┌───────────────────────────────────────────┐
│  Kiro 客户端  │ ───────────────────────────────▶ │   验证节点 EC2 (c6g.large, arm64, us-west-2) │
│ (装我方 root  │   DNS override 指向 proxy EIP     │                                             │
│  CA 后)       │                                   │   ┌─────────────────────────────────────┐   │
└──────────────┘                                   │   │ nginx  stream (listen 443 reuseport) │   │
                                                   │   │  ssl_preread on                      │   │
                                                   │   │  map $ssl_preread_server_name {      │   │
                                                   │   │    runtime.us-east-1.kiro.dev        │   │
                                                   │   │       → 127.0.0.1:8443  ★唯一 bump   │   │
                                                   │   │    <其余 SNI> → $name:443  透传       │   │
                                                   │   │    default ""  = deny                │   │
                                                   │   └───────┬──────────────────┬──────────┘   │
                                                   │           │ bump 腿           │ 透传腿         │
                                                   │           ▼                  │ (永不解密)     │
                                                   │   ┌───────────────┐          │              │
                                                   │   │ mitmproxy      │          │              │
                                                   │   │ 127.0.0.1:8443 │          │              │
                                                   │   │ (TLS 终结)      │          │              │
                                                   │   │ kiro_addon.py  │          │              │
                                                   │   └───┬────────┬───┘          │              │
                                                   │       │明文body │重加密/短路    │              │
                                                   └───────┼────────┼──────────────┼──────────────┘
                                    私网 172.31.x (同 VPC) │        │              │ 公网出口
                                                          ▼        ▼              ▼
                            ┌──────────────────────────────────┐  ┌──────────────────────────────┐
                            │ DLP 主机 <TEST_INSTANCE_ID>       │  │ 真实 Kiro 后端                 │
                            │ (m7i.2xlarge, 172.31.27.174)      │  │ runtime.us-east-1.kiro.dev    │
                            │  kiro-dlp-http  :9000  /inspect   │  │ codewhisperer/q.*.amazonaws   │
                            │    └─ DLPEngine.scan (L0–L3.5)    │  └──────────────────────────────┘
                            │  presidio-analyzer :5002 (L3)     │
                            └──────────────────────────────────┘
```

**数据流（bump 腿）**：客户端 → nginx:443（读 SNI）→ 命中 bump → `127.0.0.1:8443` mitmproxy 终结 TLS →
`kiro_addon.py` 拿到明文 body → POST 给 `172.31.27.174:9000/inspect` → DLP 引擎裁决 →
`PASS` 原样转发真实 Kiro / `REDACT` 用脱敏 JSON 改写后转发 / `BLOCK` 合成 HTTP 400 短路（**明文永不出网**）。

**数据流（透传腿）**：客户端 → nginx:443（读 SNI）→ 非 bump 域 → `$ssl_preread_server_name:443` L4 转发 →
真实后端。nginx 从头到尾**不持有密钥、不解密**，与生产透传节点行为完全一致。

## 3. 组件职责

### 3.1 nginx `stream`（四层 SNI 路由器）

- `listen 443 reuseport` + `ssl_preread on`：只读 ClientHello 里的明文 SNI，不参与 TLS 握手。
- `map $ssl_preread_server_name $backend`：
  - bump 域 → **字面** `127.0.0.1:8443`（不经 resolver，避免解析回自己成环）；
  - 其余白名单域 → `$ssl_preread_server_name:443`（单引号，落地后由 nginx `resolver 169.254.169.253` 运行时解析）；
  - `default ""` → **deny**（白名单外的 SNI 直接拒，兜住约束 C 的部分盲区）。
- 日志 `sni.log`：记录每条连接的 `sni=` / `backend=` / `status`，是「误 bump / 上游连接」的取证来源。

### 3.2 mitmproxy（bump 腿的 TLS 终结器）

- `--mode reverse:https://runtime.us-east-1.kiro.dev@127.0.0.1:8443`：反向代理模式，上游锁定真实 Kiro。
- `--set upstream_cert=false`：用本地 CA 现场签叶子（不去取真实上游证书）。
- `--set keep_host_header=true`：保留 Host 头，上游按真实域名路由。
- `--set connection_strategy=lazy`：懒连接，`BLOCK` 时压根不建立上游连接（短路的物理保证）。
- 只绑 `127.0.0.1:8443`：**绝不 0.0.0.0**——外部无法直连 mitmproxy，只能经 nginx 进来。
- systemd 单元 `kiro-mitm.service`：`User=mitm` 非 root + 全套硬化（`ProtectSystem=strict` /
  `NoNewPrivileges` / 清空 `CapabilityBoundingSet` 等）；`PYTHONUNBUFFERED=1` 确保 addon 日志进 journald。

### 3.3 `kiro_addon.py`（联动裁决 addon，方案二的大脑）

类 `KiroDLP`，挂 mitmproxy 事件钩子：

- **审查门（gate）**：`X-Amz-Target` 头 endswith `GenerateAssistantResponse` 才审。
  **刻意用 header 而非 Host 判断**——若用 Host skip，一旦 Host 头被绕过就漏审（= fail-open）；用
  目标算子判断更收紧。
- **反自环自检**：`running()` 时解析 bump 上游 IP，若解析到本机/EIP/127.0.0.1 → **拒启**（防
  nginx→mitm→nginx 自环，规格 D7）。这是正确行为，不是 bug。
- **三态处置**：
  - `PASS` → 直接放行（`responseheaders` 设 `flow.response.stream=True` 支持 event-stream 流式）；
  - `REDACT` → 校验脱敏后仍是合法 JSON（`json.loads`）→ 删 `content-md5` / `x-amz-content-sha256`
    （body 变了这些校验头必须删）→ `req.set_content(脱敏body)` 后转发；
  - `BLOCK` → `flow.response = 合成 HTTP 400`（`__type=CorpDLPBlockedException` +
    `x-amzn-ErrorType` 头 + `blocked_by_corp_dlp`）+ `flow.metadata["kiro_dlp_synthetic"]=True`，
    **上游连接从未建立**。
- **fail 语义**（严格分流，见 §5）：
  - 传输不可达（`_Unreachable`：connect refused / read 超时 / body 超限）→ 遵从 `DLP_FAIL_MODE`；
  - DLP 返回 HTTP 错误码（503/4xx，`raise_for_status()`）→ **恒 fail-closed**，无视 `open`。
- HTTP 客户端优先 `httpx`，装不上回退 `urllib`（addon 不因缺依赖而挂）。

### 3.4 DLP 判定服务（`kiro-dlp-http`，复用方案一引擎）

- 跑在 DLP 主机 `<TEST_INSTANCE_ID>`（`172.31.27.174:9000`），容器 `kiro-dlp-http`。
- 复用镜像 `kiro-dlp-engine:latest`（`ENTRYPOINT=null`，故 command 必须自带 `python -m dlp_http.server`）。
- 对象池 N×`DLPEngine`，`POST /inspect` 做裁决、`GET /health` 健康检查。
- 引擎分层 `L0 正则 → L1 secrets → L2 高熵 → L3 Presidio(PII) → L3.5 术语表`；**L4 语义 LLM 永远异步**，
  同步腿绝不触 L4（`run_async_l4=False`）——否则 `top_layer=L4` 就是「同步腿误触 Bedrock」的红线告警。
- 响应**绝不含** `matched` / `span`（原始敏感子串永不出服务）；`REDACT` 只回完整脱敏 JSON 串。

## 4. 企业 CA 三级信任结构（含两个已踩平的坑）

```
Root CA (自签，客户端唯一信任锚，无 Name Constraints)
  └─ Issuing/Intermediate CA (Name Constraints: permitted DNS=kiro.dev；CA:TRUE pathlen:0)
       └─ mitmproxy 用它现场签发叶子证书 (每次连接按目标签)
```

- **私钥永不出机**：`root.key` / `inter.key` / `mitmproxy-ca.pem` 只存在于 EC2 `/etc/mitm/certs`（权限
  600），永不进 git、永不外传。客户端只分发 `root-ca-for-clients.crt`（公开证书，无私钥）。
- **Name Constraints 挂在中间 CA**：所有 TLS 栈强制校验中间 CA 的 NC（RFC 5280 §4.2.1.10），
  物理上把这套 CA 限制为**只能伪造 `kiro.dev` 及子域**，绝无法伪造 `codewhisperer/q` 等 SigV4 域名。

### ⚠️ 坑 A：证书链不完整 → openssl code 21

`mitmproxy-ca.pem` 只放 `inter.key + inter.crt`（2 项）时，mitmproxy 现场签叶子**只下发 `[leaf]`**，
客户端手上没有中间 CA → 无法建链到 root → `unable to verify the first certificate (code 21)`。

- **源码实证**（mitmproxy 12.2.3）：`certs.py::from_files` 中 pem 内 `len(certs)>1` 才设 `chain_file`；
  `tlsconfig.py` `certificate_chain=[*chain_certs, ...]`——chain_certs 来自 pem 里叶子之后的所有证书。
- **修法**：`mitmproxy-ca.pem = inter.key + inter.crt + root.crt`（3 项）→ 下发 `[leaf, inter, root]`，
  客户端信任 root 即可完整建链。已固化进 [`gen-ca.sh`](gen-ca.sh)。

### ⚠️ 坑 B：Name Constraints 自伤 → TLSv1.3 code 48

坑 A 修好后，curl（严格 TLSv1.3）仍失败 `certificate unknown`，mitm.log 报「客户端不信任代理证书」。

- **根因**：mitmproxy 现场签叶子时**会把连接目标 IP 自动写进 SAN**（实测
  `SAN = DNS:runtime.us-east-1.kiro.dev, IP Address:<后端IP>`）。而中间 CA 的 NC 里写了
  `excluded IP 0.0.0.0/0 + ::/0`（本意禁签 IP 证书）→ 叶子的 IP-SAN 落入 excluded 子树 →
  **严格客户端判 `excluded subtree violation (code 48)`，握手直接拒**。
- **假象**：宽松 openssl 早期「看似 Verify 0」是假象，是 curl 的严格 TLSv1.3 校验才逼出真相。
- **修法**：NC **只留 `permitted;DNS.0=kiro.dev`，绝不加 excluded IP**。RFC 5280 语义：permitted 只
  约束**出现过的名称类型**——只写 permitted DNS 时，IP 类型既不 permitted 也不 excluded → 默认允许。
  于是 DNS 被牢牢收紧到 `kiro.dev`，而 mitmproxy 必需的 IP-SAN 得以放行。攻击面收紧目标已由
  permitted DNS 单独达成，excluded IP 画蛇添足且自伤。
- **教训**：证书验证**必须用 TLSv1.3 严格客户端**（`curl --cacert` / `openssl -verify_return_error`），
  宽松校验会放过 code 48。

## 5. fail 语义（规格 D3/D4）—— 严格分流

addon 把两类故障严格区分，绝不混淆：

| 故障类型 | 判定依据 | `DLP_FAIL_MODE=closed`（默认，生产） | `DLP_FAIL_MODE=open`（仅灰度） |
|---|---|---|---|
| **传输不可达** | connect refused / read 超时 / body 超 `DLP_MAX_BODY_BYTES` | 503 `dlp_unreachable`，**上游零命中** | 200 放行（**未审查**，生产禁用） |
| **DLP 返回 HTTP 错误码** | `raise_for_status()` 命中 503/4xx | **恒 503 `dlp_error`**（无视 open） | **仍恒 503**（服务自认无法扫描 = 恒 closed） |

**设计理由**：
- 「服务连不上」是环境故障，可由运维选择灰度放行（open）应急；
- 「服务活着但明确说它扫不了」（HTTP 503/4xx）意味着这条流量**没被审查过**，放行 = 裸奔，因此
  **无论 fail 模式如何都必须 closed**——这是 D4 的核心。
- `open` 模式**仅用于灰度**，生产环境必须 `closed`。

## 6. 安全红线（不可协商，来自设计评估与实测）

> 这些是方案二运行期间**任何时候都不能破坏**的不变量，破坏即停止/回滚。

1. **私钥不出机**：`root.key` / `inter.key` / `mitmproxy-ca.pem` 仅在 EC2 生成、仅存 `/etc/mitm/certs`
   600、永不进 git、永不外传。客户端只装 `root-ca-for-clients.crt`。
2. **NC 只 permitted DNS=kiro.dev**：绝不加 excluded IP（坑 B）；这套 CA 物理上只能伪造 kiro.dev 子域。
3. **mitm 只绑 127.0.0.1:8443**：绝不 0.0.0.0；外部只能经 nginx。
4. **透传腿绝不解密**：§3 红线——透传域 issuer 若出现「我方中间 CA」= 误 bump，立即停止回滚。
5. **反自环**：addon 上游解析 IP 不含本机/EIP/127.0.0.1，命中自环拒启。
6. **BLOCK 用 HTTP 400**：区别于上游 401/403，避免「机密已外泄被上游拒」与「本地拦截成功」状态码混淆。
7. **同步腿绝不触 L4**：`top_layer=L4` 是红线告警；L4 语义审查永远异步，且**只用 VPC 内/自托管 LLM，
   绝不用第三方 LLM**（那是二次外发）。本轮 L4 用 Bedrock 仅做功能标定，**非生产配置**。
8. **绝不 `NODE_TLS_REJECT_UNAUTHORIZED=0` / `rejectUnauthorized:false`**：pinning 判定失败就回滚，
   绝不用禁用校验来「绕过」。
9. **绝不碰生产 SNI 透传节点**（us-east-1，实例 ID / EIP 见内部部署记录）：方案二是独立
   验证节点，独立 EIP/IAM/state，`cleanup.sh` 只删本次资源。

## 7. 与方案一的对比

| 维度 | 方案一（LiteLLM opt-in 网关） | 方案二（选择性 bump MITM，本文） |
|---|---|---|
| 拦截点 | LiteLLM 终止网关（`base_url` 重定向） | nginx+mitmproxy 透明 MITM |
| 客户端改动 | 必须改 `base_url` | 只需信任企业 root CA，**无需改配置** |
| **能否覆盖 Kiro** | ❌ Kiro 硬编码 provider、不能改 base_url | ✅ 透明拦截，能覆盖 |
| 覆盖范围 | 所有主动接入网关的 agent/SDK | 仅 Kiro 推理腿（选择性 bump） |
| DLP 引擎 | **同一套** `kiro-dlp-engine` | **同一套**（复用，只是拦截点不同） |
| TLS 风险 | 无（不解密，客户端自己终止到网关） | 有（明文集中在一台 EC2，靠 CA 三级链 + NC + 硬化收敛） |
| 合规负担 | 低（opt-in，用户知情） | 高（需正式安全评审 + 员工告知 + CA 分发） |
| 部署形态 | 网关容器 | 独立 EC2（nginx + mitmproxy + systemd） |
| 定位 | 治「可配 base_url 的自研 agent」 | 治「硬编码 provider 的 Kiro」 |

**互补关系**：两者不是替代，是**分层**。第 0 层永远是 opt-out + `.kiroignore` + default-deny 出口
白名单 + prompt logging（不碰 TLS）；方案二/MITM 只在「外发前必须同步硬阻断」是硬需求时作为补充层，
且必须全部前置到位（4 项 pinning/认证/host/索引必测 + CA 分发 + 正式评审）。

## 8. 本轮作用域与诚实边界

- **测试作用域（用户已定）**：仅 SSM，proxy 本机自测——不开公网 443、本轮不在 Kiro 桌面端实测。
  所有 `curl` / `openssl` 从 proxy EC2 本机打 `127.0.0.1`。
- **已验证**（详见 [`方案二-03-测试报告.md`](方案二-03-测试报告.md)）：四层测试全绿——bump 解密、透传红线、
  三态联动（含 wire-byte 铁证 + 真实上游交叉核对）、fail 模式四子测。
- **未做/遗留**：
  - §6 证书固定（pinning）判定：推迟到真实 Kiro 桌面端测（本轮不测）；
  - 真实 Kiro 客户端端到端：需在客户端主机装 root CA 并让各 TLS 栈（Chromium / Node/Electron /
