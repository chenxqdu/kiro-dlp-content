## 2. §2 bump 腿解密（证明 TLS 拦截生效）

```bash
# 严格 TLSv1.3 客户端（这是逼出 code 48 的关键，宽松 openssl 会放过）
curl -v --cacert /etc/mitm/certs/root.crt --resolve runtime.us-east-1.kiro.dev:443:127.0.0.1 \
     https://runtime.us-east-1.kiro.dev/  2>&1 | grep -E 'SSL certificate verify|HTTP/'
# openssl 严格校验（-verify_return_error 让 code!=0 直接失败）
echo | openssl s_client -connect 127.0.0.1:443 -servername runtime.us-east-1.kiro.dev \
     -CAfile /etc/mitm/certs/root.crt -verify_return_error 2>&1 | tee /tmp/bump.txt >/dev/null
grep -E 'Verify return code|issuer=' /tmp/bump.txt
```

**实测**：
- curl：`SSL certificate verify ok` → 升 HTTP/2 stream；
- openssl：`Verify return code: 0 (ok)`，issuer 含 `Kiro-DLP-Verify Issuing CA`（我方中间 CA）；
- 证书链 `leaf → inter → root` 完整下发。

**反例**（用系统 CA 不带我方根）→ `unable to verify`（非 0）：证明这确实是我们伪造的证书链。

### 4.2 Tier B —— 本地假上游 wire-byte 铁证（`tests/tier_b_wire.sh`）

> **为何是核心**：无有效 token 时无法真跑上游，但「上游实际收到什么字节」与上游无关，是「是否改写 /
> 是否放行 / 是否调了 DLP」的硬证明。本地 `echo_upstream` 记录到达上游的真实字节，临时 mitmdump（`9443`）
> reverse→echo（`18080`）加载**同一** addon，与生产 443/8443 完全隔离。

| 用例 | 断言 | 实测 |
|---|---|---|
| **B-PASS** | 上游收到的 body 与输入**逐字节一致**（`cmp -s`） | ✅ 未改写 |
| **B-REDACT** | 上游收到 `我叫[REDACTED:PERSON]，电话 [REDACTED:CN_PHONE]`；深度遍历叶子 + 双形态（明文 & `\uXXXX`）匹配确认 `13800138000`/`张伟` 消失；信封结构完整 | ✅ 明文 PII 清除 |
| **B-BLOCK** | 上游 body 文件**根本不存在**（`[[ ! -f UP_BODY ]]`）+ client 得 400 | ✅ 机密零出网 |

### 4.3 Tier C —— 真实上游交叉核对（`tests/tier_c_real_upstream.sh`）

> 与 Tier B 互补：Tier C 走**生产** 443→8443→**真实** `runtime.us-east-1.kiro.dev`，配**假 Bearer**。
> 靠响应来源域区分「BLOCK 是否在触达真实 Kiro 前短路」。生产 mitm 不改动。

| 用例 | 响应来源 | 实测 |
|---|---|---|
| **PASS**（普通内容 + 假 token） | **真实 AWS**：Coral `ValidationException` + 真 `x-amzn-requestid` | ✅ 请求真到上游 = 转发路径 + 真实 TLS 腿贯通 |
| **BLOCK**（含 RSA 私钥 + 假 token） | **我方合成**：`CorpDLPBlockedException` + `x-amzn-ErrorType` 特征头 | ✅ 含密钥请求从未出网 |

**物理证明**：两响应的 errortype **来源域不同**（AWS vs 我方）——BLOCK 的机密内容从未离开代理。
这正是 BLOCK 用 **HTTP 400**（而非上游的 401/403）的意义：状态码 + 特征头 + 无上游连接，多重可区分。

## 5. §5 fail 模式（规格 D3/D4，`tests/tier_fail_modes.sh`）

全程走临时 `9443` 实例，绝不碰生产 443/8443。四子测：

| 子测 | 故障 | fail 模式 | 期望 | 实测 |
|---|---|---|---|---|
| 1 | hard-down（connect refused） | closed（默认） | 503 `dlp_unreachable` + 上游零命中 | ✅ |
| 2 | hard-down | open（灰度） | 200 放行（未审查）+ 上游命中 | ✅ |
| 3 | slow（睡 30s > `DLP_TIMEOUT` 3s） | closed | read 超时 = 不可达 → 503 | ✅ |
| 4 | **DLP 返 HTTP 503** | **open** | **恒 fail-closed** 503 `dlp_error`（无视 open，D4） | ✅ |

mitm.log 逐行佐证子测 4 走的是 `HTTPStatusError 503 → KIRO-FAILCLOSED reason=dlp_error` 分支，而非
`unreachable`——证明 addon 把「传输不可达」与「HTTP 错误码」严格分流。

## 6. §6 pinning 判定（本轮不测，留判据）

本轮作用域是「仅 SSM、proxy 本机自测」，不在 Kiro 桌面端实测。将来在真实 Kiro 客户端主机（仅该主机）
装 root CA + DNS override 指向 proxy EIP 后，判据三分：

- 正常出流量、收到模型响应 → **未 pinning**，MITM 可行；
- `UnknownIssuer`/证书不信任 → 信任配置问题，**可修**（补装 root CA 到对应 TLS 栈）；
- 干净 TLS 断链（非 issuer、握手被应用层直接拒）→ **pinning 生效，MITM 不可行 → 回滚**。
- **绝不** `NODE_TLS_REJECT_UNAUTHORIZED=0` 绕过。

## 7. 两个证书坑复盘（都靠「读 mitmproxy 源码 + curl 严格校验」定位）

### 坑 A：证书链不完整 → openssl code 21

- **现象**：`mitmproxy-ca.pem` 只放 `inter.key+inter.crt` 时，mitmproxy 现场签叶子只下发 `[leaf]`，
  客户端无中间 CA → 建链失败 `unable to verify the first certificate (code 21)`。
- **源码实证**（mitmproxy 12.2.3）：`certs.py::from_files` 中 pem 内 `len(certs)>1` 才设 `chain_file`
  → `default_chain_certs` = pem 全部证书；`tlsconfig.py` `certificate_chain=[*chain_certs, ...]`。
- **修法**：`mitmproxy-ca.pem = inter.key + inter.crt + root.crt`（3 项）→ 下发 `[leaf, inter, root]`。
  已固化进 [`gen-ca.sh`](gen-ca.sh) 第 91 行 + 头部注释。

### 坑 B：Name Constraints 自伤 → TLSv1.3 code 48

- **现象**：坑 A 修好后 curl（严格 TLSv1.3）仍 `certificate unknown`，mitm.log「客户端不信任代理证书」。
- **根因**：mitmproxy 现场签叶子**会把连接目标 IP 自动写进 SAN**（实测
  `SAN=DNS:runtime.us-east-1.kiro.dev, IP Address:<后端IP>`）；中间 CA 的 NC 里写了 `excluded IP
  0.0.0.0/0 + ::/0` → 叶子 IP-SAN 落入 excluded 子树 → 严格客户端判 `excluded subtree violation (code 48)`。
- **假象警告**：宽松 openssl 早期「看似 Verify 0」是假象，curl 的严格校验才逼出真相。
- **修法**：NC **只留 `permitted;DNS.0=kiro.dev`，绝不加 excluded IP**（RFC 5280：permitted 只约束
  出现过的名称类型，只写 permitted DNS 时 IP 默认放行；DNS 仍被物理收紧到 kiro.dev）。已固化进
  [`gen-ca.sh`](gen-ca.sh)。
- **教训**：证书验证**必须用 TLSv1.3 严格客户端**（`curl --cacert` / `openssl -verify_return_error`）。

### 测试假象踩坑（记牢，非产品 bug）

§5 子测 4 首轮**误报**（期望 503 得 200）——根因是 fake DLP 用单线程 `socketserver.TCPServer`，子测 3
的 `time.sleep(30)` 阻塞了后续请求，addon 误判超时（不可达 → fail-open 放行）而非收到 503。
**修法**：故障注入的 mock server 必须用 `ThreadingHTTPServer`（每请求独立线程），且每个子测起独立进程 +
self-check 直连确认 mock 真返回目标码，再断言 addon 分支（`grep mitm.log`）。修后四子测全绿——
**addon 逻辑一直是对的，那是测试脚手架的假象**。

### 8.0 被测对象与断言口径（为何与方案一不同）

方案二压测打的是 **`/inspect` 纯裁决薄服务**（`http_service/server.py`）——**不转发上游、不接 LLM**，
恒返回 `HTTP 200 + verdict JSON`（错误路径才 503/413/400）。由此两点与方案一（网关 HTTP 400）不同：

1. **拦截判据看返回 JSON 的 `verdict`**（`BLOCK`/`REDACT`/`PASS`），不是方案一的 HTTP 400。测的是
   **引擎裁决延迟净成本**——不含网关 + 上游转发，故比方案一 §9 数字更纯（也更低）。
2. **泄漏语义按真实 MITM 数据流判定**（addon 依 verdict 决定写什么给上游）：`BLOCK`→短路不发上游（绝不泄漏）；
   `REDACT`→把 `redacted_body` 写回上游（泄漏 **iff** 脱敏体仍含明文探针）；`PASS` 一个攻击向量→addon
   转发**原始明文**（=泄漏）。k6 的 `plaintext_leak` 与契约哨兵 `contract_leak`（响应体出现 `matched`/`span`）
   **必须恒为 0**。

### 8.6 诚实边界

1. **`/inspect` 延迟 ≠ MITM 真链路延迟**：本节测的是**引擎裁决净成本**，**不含** MITM 的 TLS 劫持 + 转发上游——
   那部分是 §4.4 Tier D 的**定性**证据（verdict + `top_layer` 双断言），不是分位数。要端到端时延须在真机链路上另测。
2. **单副本 Presidio 单核瓶颈**（承接方案一 §8.6 遗留①）：长文本高并发下 L3 是吞吐上限；§8.2 拐点是**合法短文本**口径，
   长文本会更早塌方。生产长文本须多 worker 扩 Presidio。
3. **同机发压噪声**：k6 与被测同主机（`taskset` 分核），尾延迟（p99.9/max）含抢核噪声偏高；但拦截正确性结论
   （泄漏=0 / 误杀=0 / 处置率=100%）不受影响。
4. **prod-default（L4 关）口径**：本压测节不覆盖 L4 语义腿延迟（Bedrock 后端数据出 VPC，仅功能验证）；L4 功能三态
   由 §4.5 Tier E 专测，§4.1 Tier A 另验「同步腿（off/async 口径）不误触 Bedrock」。
